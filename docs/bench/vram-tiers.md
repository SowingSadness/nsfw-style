# Замер: влезают ли тарифы `VRAM12` / `VRAM16` (пик VRAM по `nvidia-smi`)

Имена пресетов обещают карту: `VRAM8-*` — 8 ГБ, `VRAM12-*` — 12 ГБ, `VRAM16-*` — 16 ГБ.
Этот замер проверяет, что обещание не врёт: **фактический пик VRAM процесса не выше тарифа**.

Машина: **RTX 4080 16 ГБ VRAM / 63.6 ГБ RAM**, Windows 11, torch 2.8.0+cu129,
diffusers 0.43.0.dev0, numpy 2.5.4, `HF_HUB_OFFLINE=1`, `PYTHONIOENCODING=utf-8`,
fp8-кэш трансформера на диске (`cache/models/fp8_transformer`), прогретый page cache весов.
Дата: **2026-11-16**. HEAD: `6dbe54f refactor(names): профили VRAM8/VRAM12/VRAM16 в коде и тестах`.

Условия прогонов (одинаковые для всех пяти):

- референс — **синтетический квадрат 768×768** (`prompts/_tiers/image1.png`, PIL: рамка, эллипс,
  прямоугольник; sha256 `4942495b1364…`), промт `prompts/_tiers/prompt.txt` = `tests/texts/exp3.txt`;
- `--aspect 16:9` → кадр 16:9 при `size_px` пресета, `--seed 1`, LoRA **0.0** (базовый Qwen без
  FUSAL — так задано в самих пресетах), энкодер `heretic` (Qwen3-VL-8B, стриминг на GPU,
  `prefetch=4`, веса `cache/models/weights/heretic-te`, 16.33 GiB);
- один процесс на пресет, команда:

```bash
PYTHONIOENCODING=utf-8 HF_HUB_OFFLINE=1 .venv/Scripts/python.exe -m qwenstyle run \
    --config <ПРЕСЕТ> --aspect 16:9 --seed 1 \
    --prompt-file prompts/_tiers/prompt.txt --input prompts/_tiers/image1.png \
    --out out/_tiers/<имя>.png
```

**Как мерялся пик.** Не строкой `[done] … peak vram` (это `mem_get_info()` уже после выгрузки
весов — она всегда показывает 1.3–1.4 GiB и к тарифу отношения не имеет), а внешним сэмплером:
`nvidia-smi --query-gpu=memory.used --format=csv,noheader,nounits` каждые **0.5 s** в фоне, max по
всему прогону. Числа в таблице — **полное `memory.used` карты**, то есть вместе с рабочим столом
(перед прогонами занято **1797–2371 MiB**: браузер/оболочка). Это худший, «честный» вариант для
вопроса «влезет ли на карту N ГБ»; вклад самого пайплайна — колонка «свой процесс».

## Факт против имени

- **`VRAM12-preview` — влезает с запасом.** 7.17 ГиБ из 12 (запас 4.8 ГиБ). `768p` +
  `offload: group`: веса трансформера в VRAM не держатся, поэтому пик ниже, чем был у прежнего
  `strong-preview` с `offload: none` (13.1 ГиБ по `docs/bench/presets.md`, правда на квадратном
  кропе 768×768) — тариф 12 теперь честный. Цена — генерация 17 s вместо ~9 s без offload, но это черновик.
- **`VRAM12-release` — влезает, но с меньшим запасом** (8.26 из 12, 3.7 ГиБ). 960p/25 шагов с
  `offload: group` — 71 s. Запас уходит не на веса (их в VRAM ~0.2 ГиБ), а на **активации**:
  это единственная статья, которая растёт с числом токенов (1822 промт-токена, 1696×960 =
  7590 латентных). Рекомендации не требуются, но `VRAM12-release` — ближайший к своему тарифу
  пресет из пяти: если когда-нибудь захочется 1080p на 12 ГБ, это будет уже 12+ ГиБ и потребует
  либо `size_px` вниз, либо `kv_cache: false` (считать префикс заново).
- **`VRAM16-preview` — влезает с запасом** (11.98 из 16, 4.0 ГиБ) **и это самый «дорогой» по
  VRAM превью-профиль**: `offload: none` держит fp8-веса (6.6 ГиБ) в VRAM, зато 8 шагов идут 15 s.
  Связка `offload: none` + `kv_cache: offload` (её ввёл шаг 1) работает как задумано: без KV в RAM
  было бы +2.13 ГиБ, то есть ~14 ГиБ и почти впритык.
- **`VRAM16-release` — влезает** (12.85 из 16, 3.2 ГиБ). Нативный 1440p (2560×1440, 10800 токенов)
  уложился в **8.2 s/шаг** (205 s на 25 шагов) — заметно лучше прежних 16–17 s/шаг из `AGENTS.md`
  §4; разница объясняется тем, что 7.14 ГиБ префиксного KV живут в RAM (`kv_cache: offload`),
  а не в VRAM. Спилла активаций нет.
- **`VRAM16-4k-fast` — влезает с большим запасом** (7.68 из 16, 8.3 ГиБ). 1088p идёт 96 s
  (3.8 s/шаг), ESRGAN ×1.985 — 2.0 s, пик апскейлера на общем фоне незаметен, потому что пайплайн
  перед ним уже выгружен. Быстрый 4K честно стоит вдвое дешевле нативного 1440p по VRAM.

Итог: **пять из пяти пресетов укладываются в свой тариф**, ни один не «впритык» по критерию
«меньше 10 % запаса». Ничего чинить не нужно; правок пресетов по результатам замера не вносилось.

## Роль `kv_cache: offload` (12 ГБ: один и тот же кадр с KV в RAM и в VRAM)

`VRAM12-release` — единственный пресет, у которого запас невелик, поэтому на нём же проверено,
что даёт `kv_cache: offload` (один дополнительный прогон, `--set generation.kv_cache=true`):

| `kv_cache` | пик VRAM, МиБ | пик VRAM, ГиБ | генерация, 25 шагов | PNG sha256 |
|---|---|---|---|---|
| `offload` (в пресете) | **8454** | **8.26** | 71 s | `28bbc899c7f4…` |
| `true` (KV в VRAM) | **11596** | **11.32** | 68 s | `28bbc899c7f4…` |

- **+3.07 ГиБ VRAM** за KV в VRAM (строка `[kv]` обещала 3.22 ГиБ — сходится), и это ровно тот
  запас, который отделяет `VRAM12-release` от «впритык»: 11.32 из 12 ГиБ при живом рабочем столе
  (1.8–2.4 ГиБ) — уже риск OOM на настоящей 12-гиговой карте.
- **Цена офлоада — 4 % времени** (71 s против 68 s), а не 13 %, как в `docs/bench/kv-cache-offload.md`
  на 3 референсах: чем короче префикс, тем дешевле подкачка.
- **Кадр бит-в-бит**: sha256 PNG совпадает. То же и у пары `VRAM12-preview` (`offload: group`) /
  `VRAM16-preview` (`offload: none`) — файлы идентичны (`96a12451f5d2…`), то есть `offload`
  действительно меняет только раскладку памяти, а не арифметику.

## Оговорки

- RAM-часть тарифа не мерялась (в задаче — только VRAM). Косвенно: префиксный KV в RAM занимает
  2.13 / 3.22 / 2.13 / 7.14 / 4.10 ГиБ по пресетам, энкодер стримится по модулям
  (≤1–2 ГиБ), так что 32 ГБ у `VRAM12-*` и 64 ГБ у `VRAM16-*` имеют запас.
- `--aspect 16:9` с квадратным референсом: кадр считается от `size_px`, референс подгоняется
  `fit_cover`. На 16:9-референсе того же промта площади больше на 1.78×, и пик VRAM вырастет
  примерно на активации (+1–2 ГиБ на 1440p) — тариф это всё ещё держит, но запас `VRAM12-release`
  в таком сценарии станет ~2 ГиБ.
- Замеры — один кадр на пресет, `seed=1`; WDDM может дать первый кадр в 2–3 раза медленнее
  последующих, поэтому времена в таблице — «как есть», без повторов.
