# AGENTS.md — контекст проекта для агентов

Локальный **NSFW-style**: стилизация/правка/генерация на **Qwen-Image-2.1**, опционально аниме-адаптер
FUSAL (R80 v2), img2img с сохранением композиции. Inference только локальный, на одной RTX 4080 16 ГБ.
Точка входа — пакет `qwenstyle`
(`python -m qwenstyle gen|run|selftest|env|cache|models|compare-upscale|bench|config`),
описание результата и раскладки памяти — `README.md`.

Этот файл — обязательные правила для любого агента/разработчика, который меняет код в репозитории.

---

## 0. Профили машин: что советовать

Профиль — единственный ответ на вопрос «что советовать этой машине». Данные — `qwenstyle/profiles.py`
(`PROFILES`, `profile()`, `disk_estimate()`), пресеты — `qwenstyle/presets/<профиль>-*.yaml`.
Публичный обзор для пользователя — `README.md` («Ваша машина → профиль»), измеренные времена —
`docs/bench/presets.md`.

| железо | профиль | пресеты | диск | целевой рендер |
|---|---|---|---|---|
| 8 ГБ VRAM / 16 ГБ RAM | `weak` | `weak-preview`, `weak-release`, `weak-preview-anime`, `weak-release-anime` (480p/640p, энкодер **CPU** + диск-стриминг, `offload: group`) | ≈ 75 ГиБ | 1080p (ESRGAN ×1.69) |
| 16 ГБ VRAM / 32 ГБ RAM | `strong` | `strong-preview`, `strong-release`, `strong-preview-anime`, `strong-release-anime` (768p без offload / 960p с `offload: group`, энкодер на GPU) | ≈ 55 ГиБ | 1440p (ESRGAN ×1.5) |
| 16 ГБ VRAM / 64 ГБ RAM | `flagship` | `flagship-preview`, `flagship-preview-anime`, `flagship-release`, `flagship-release-anime`, `flagship-4k-fast` | ≈ 181 ГиБ | 4K UHD (2160) |

Аниме — опция: ветки `*-anime` включают адаптер FUSAL 0.7; пресеты без суффикса работают без
стилевого адаптера.

Жёсткие правила рекомендаций:

- **8 ГБ VRAM — только `weak-*`**: там энкодер идёт на CPU (`encoder.device: cpu` + `stream: true`) и
  везде включён `offload: group`. 960p/1440p, FLUX.2 и H3-Image этой машине не советовать.
- **32 ГиБ RAM — не советовать H3-Image** (`h3-image`, флагманский профиль): групповой offload держит
  30.9 ГиБ fp8-трансформера в RAM, на 32 ГиБ это упирается в спилл.
- **Дефолтный энкодер — `heretic`** (`encoder.name: heretic`, `cache_tag: heretic`): только на его
  conditioning LoRA обучалась. `base` — осознанным флагом (`--text-encoder base` или
  `--set encoder.name=base`), и это другой ключ кэша (тег `_te-heretic` в имени файла).
- **Новый пресет обязан попасть в профиль** — в `presets=…` (и при необходимости в `repos`/`disk_gib`)
  `qwenstyle/profiles.py`; иначе он существует только для разработки и должен быть помечен dev-only
  в `docs/DEVELOPMENT.md`. Публичные имена — `<family>-<stage>[-anime]`; `gen --preset` разрешает
  шорткаты (`strong` = `strong-release`, `strong-anime` = `strong-release-anime`).
- **Проверка установки — `selftest`**, а не эталоны кадров: `python -m qwenstyle selftest --profile
  <имя>` (окружение → веса профиля → один рендер 480p/4 шага). `models download --profile … --probe`
  проверяет доступ к весам без полной загрузки.
- **В README и в советах — только измеренные числа** из `docs/bench/presets.md` (наша машина:
  RTX 4080 16 ГБ / 63.6 ГБ RAM) и `profiles.py`; не обещать «влезет на любой GPU».

### Политика кешей: `cache/embeds` ↔ `cache/models`

| ветка | что внутри | правила |
|---|---|---|
| `cache/embeds/` | вычисленный conditioning: `embeds_<md5>_<sha>…_<W>x<H>.pt` (+ `.json`), `text_embeds_…` (FLUX.2/H3), `_stale/` | **вытесняется**: `cache prune … --apply` (без флага — только план) и автоматически политикой `cache_supersede` отложенной задачей в конце прогона; одна запись на сетку, смена `--size`/`--resolution`/`--aspect` ничего не удаляет |
| `cache/models/` | `fp8_transformer*` (квантование трансформеров) и `weights/` (heretic 8B/32B, ESRGAN) | **не вытесняется никогда**: пересборка только `--rebuild-fp8-cache`; `cache list|show|prune` в эту ветку не заглядывают |

`hf-cache/` (`HF_HOME`) — исходные веса, тоже не чистится автоматически. Ключ эмбеддингов от путей
не зависит: переезд `cache/*.pt` → `cache/embeds/` — это путь, а не другая математика.

## 2. Обязательные правила

### R1. Кэшировать параметры запуска — всегда

Любой шаг, который стоит **больше ~1 с или больше ~100 МБ** вычислений, обязан иметь дисковый кэш.
Повторный запуск с теми же параметрами не должен пересчитывать ничего заново.

- **Ключ кэша** = все параметры, влияющие на результат, без исключений. Для текущего пайплайна:
  текст промта, **sha256 входного изображения** (см. долг D1), `crop_w`/`crop_h`, `--resolution`,
  `--steps`, `--seed`, `--lora-scale`, `--fp8`, имена+ревизии (commit hash) базовой модели и LoRA,
  версии torch/diffusers/transformers.
- **Имя файла**: `<stage>_<hash16>_<краткие параметры>.<ext>`, например
  `cache/embeds_<hash>_1376x768.pt` (как сейчас) или `cache/latents_<hash>_seed20261113.pt`.
- **Рядом** класть `<то же имя>.json` с полным набором параметров и временем создания — чтобы кэш
  можно было инспектировать и инвалидировать без чтения бинаря.
- **Запись атомарная**: писать в `*.tmp`, затем `os.replace()`. Иначе прерванный запуск оставит
  битый кэш, который потом молча отравит результат.
- **Hit**: печатать, откуда взято (`embeddings из кэша <path>`), и **не** пересчитывать.
  **Miss**: печатать, какой именно параметр изменился (сравнив метаданные с ожидаемыми).
- Никогда не удалять/перезаписывать чужой кэш молча: в момент записи не удаляется ничего. Очистка —
  `cache prune --apply` (вручную, R2) или политика вытеснения `cache_supersede` отложенной задачей
  в конце прогона (R2).

Что инвалидирует кэш эмбеддингов, а что нет (код: `config.py::embeds_key` +
`pipeline.py::EMBEDS_HIT_FIELDS`):

| изменение | переиспользуется ли старый `.pt` | механизм |
|---|---|---|
| текст промта, картинка, `crop` (`--size`/`--resolution`/`--aspect`), тег энкодера | **да** | в имени файла |
| `encoder.dtype`, `encoder.device` | **да** | сегменты `-fp16` / `-dev-cuda` в имени. `device=auto` на машине с CUDA разрешается в `cuda`, поэтому запись по умолчанию получает `-dev-cuda`; `cpu`/`bfloat16` без сегмента — легаси-записи, они остаются валидными |
| `encoder.repo`/`encoder.revision`, `CACHE_SCHEMA` | да, но только сверкой сайдкара | при попадании `.json` сверяется по белому списку; расхождение = промах с печатью изменившегося поля (`[cache] miss: изменился encoder_device …`). Поле `schema` пишут только записи нового формата: старые сайдкары его не содержат и считаются валидными (`EMBEDS_HIT_DEFAULTS`), поэтому bump `CACHE_SCHEMA` инвалидирует **только новые записи**, а legacy-сайдкары — нет |
| `--seed`, `--steps`, `--lora-scale`, `--fp8`, `--offload`, `encoder.stream`/`prefetch`/`pin_memory`/`lookahead` | **нет** (бесплатные оси) | раскладка памяти и сэмплер, не conditioning |

Причина: GPU-энкод ≠ CPU-энкод по округлениям (`max|diff|` 128.0 по элементам на слоях 9/18/27),
поэтому `dtype`/`device` — часть идентичности записи, а не «режим».

### R2. CLI-инструментарий — обязателен

Для ручного запуска и обслуживания кэшей в проекте **один** CLI — `python -m qwenstyle`, а не набор
одноразовых скриптов в корне. Подкоманда = модуль `qwenstyle/cmd/*.py` (отдаёт `NAME`, `HELP`,
`add_args()`, `run()`), подкоманды собираются автоматически (`qwenstyle/cli.py`), поэтому новая
команда не правит ядро. Минимальный контракт:

```
python -m qwenstyle gen --preset strong --prompt <имя> [--seeds 84,32-38 | --count N]
                                # главная точка входа: папка prompts/<имя>/ (prompt.txt + image*)
                                # -> out/<имя>/gen-YYYYMMDD-HHMM/ (кадры, run.log, meta.json в корне)
                                # --dry-run — план без весов; --no-logs — без run.log
python -m qwenstyle run [--preview | --size 768p | --resolution N] [--aspect 16:9|4:3|1:1] [--prompt-file ...] [--input ...] --out ...
                                # одиночный кадр: все флаги старого run_style.py + --config/--set
                                # --input необязателен: нужен ли референс, решает `Capabilities.requires_image`
                                # --dry-run (план без весов)
                                # лог: <кадр>/run.log + meta.json рядом с кадром; --no-logs — не создавать
python -m qwenstyle selftest --profile weak|strong|flagship   # установка: окружение, веса профиля, рендер 480p/4 шага
python -m qwenstyle env         # версии, CUDA/GPU/VRAM/RAM, offline-режим, счётчики кэшей, свободный диск
python -m qwenstyle models list|probe <repo> [--offline]   # реестр бекендов и зондирование без скачивания
python -m qwenstyle models download --profile <имя> [--dry-run] [--probe] [--yes]   # план/проверка доступа/загрузка
python -m qwenstyle models download <repo> [--dry-run] [--yes]   # план файлов/размера, само скачивание только с --yes
python -m qwenstyle cache list [--resolution 640] [--json]  # файлы в cache/embeds, размер, ключевые параметры, возраст
python -m qwenstyle cache show <name|prefix>                # метаданные записи (сайдкар .json)
python -m qwenstyle cache prune [--keep-per-resolution 1] [--group-by prompt|image]
                                [--older-than 30d] [--legacy] [--all] [--apply]
python -m qwenstyle compare-upscale --input <png> --height 960   # метрики апскейлеров на одном кадре
python -m qwenstyle bench vram --resolution 640 --input <png>   # пик VRAM/RSS по фазам (бывший tools/measure_vram.py; --input обязателен)
python -m qwenstyle config show base [--set a.b=c] [--explain-params]   # резолвленный RunConfig (единственный источник)
hf cache verify <repo>                                  # целостность весов (вне пакета)
```

Пресеты — `qwenstyle/presets/*.yaml`, только данные (`extends:` = deep-merge, без кода), читаются
через `RunConfig.from_profile(<имя>)`. **Публичные (13)** — `weak-*` / `strong-*` (по 4) и 5
флагманских; они адресуются профилем машины (`profiles.py`, §0) и только они попадают в README.
Остальные — dev-пресеты (см. `docs/DEVELOPMENT.md`), публичные шаги на их имена не опираются:

| пресет | что это | модель / шаги / кэш точности |
|---|---|---|
| `base` | профиль по умолчанию: R80 v2 | `Qwen/Qwen-Image-2.1`, 25 шагов, fp8, `cache/fp8_transformer` |
| `preview-qwen` | черновик Qwen для итераций по промту | `extends: base`, `size_px: 480` (864×480 при 16:9), 8 шагов |
| `turbo` | distill-профиль | transformer из `Qwen/Qwen-Image-2.1-Turbo` + Turbo E6 R128 LoRA, 8 шагов (расписание `sample_sigmas`), `cache/fp8_transformer_turbo` |
| `flux2` | базовый FLUX.2 klein | `Flux2KleinPipeline` + `Qwen3ForCausalLM`, `conditioning=internal`, `image_inputs=multi`, fp8, `cache/fp8_transformer_flux2` |
| `preview` | черновик FLUX.2 | `extends: flux2`, `size_px: 768` (1376×768), 8 шагов, offload не нужен (33 с) |
| `demo` | быстрая демонстрация | `extends: flux2`, `size_px: 960` + ESRGAN до `target_height: 1440` → 2592×1440 за ~61 с |
| `full-flux2` | финальный кадр FLUX.2 | `extends: flux2`, `size_px: 1440` (2592×1440) + `offload: group`, `offload_blocks: 2` → 121 с, пик VRAM 15.7 GiB |
| `h3-image` | MiniMax-H3-Image: T2I и edit одним пайплайном | `MiniMaxAI/MiniMax-H3-Image` (33.13B), 6 шагов PDD, fp8 (30.9 GiB) + `offload: group`, `cache/fp8_transformer_h3_image`, LoRA нет, энкодер Qwen3-VL-32B (`h3qwen32-heretic`) |

Политика кэша эмбеддингов (важно):
- **одна запись на каждое разрешение**, разные разрешения сосуществуют и **никогда не удаляются
  при смене `--resolution`/`--preview`** — смена разрешения только досоздаёт новую запись;
- **вытеснение = `cache_supersede`** (`RunConfig.cache_supersede`, `qwenstyle/cleanup.py`): политика
  `none|prompt|image|pair`, умолчание **`pair`**. Новая пара (промт, картинка) делает прошлые записи
  этой пары устаревшими, и они удаляются **отложенной задачей в самом конце прогона** — после
  генерации, апскейла и сохранения кадров, никогда в момент записи кэша и никогда во время работы;
  `crop`/`--size`/`--resolution`/`--aspect` в вытеснении **не участвуют** (иначе каждое переключение
  резолюции стоило бы нового энкода); варианты `-fp16`/`-dev-cuda` друг друга **не вытесняют**
  (нужны для сравнения и отката); запись текущего прогона не удаляется никогда;
- ⚠️ следствие `pair`: два одновременных `run` с **разными промтами на одной картинке** могут
  вытеснить кэш друг друга (второй удалит запись первого). Эскапей — `--set cache_supersede=none`
  (или `prompt`/`image`, чтобы сузить политику);
- `cache prune` без `--apply` — это только план; по умолчанию он хранит **самый свежий кеш
  на каждое разрешение** внутри группы (промт+картинка+энкодер+dtype+device) и другие промты не трогает;
  `--group-by image` — строже: ровно один кеш на разрешение по картинке, старые промты вытесняются;
- `cache prune --apply` остаётся для ручной уборки (дубли на одном crop, `--older-than`, `--legacy`);
- мёртвые записи старой схемы (без хеша картинки) чистятся только явно: `cache prune --legacy --apply`;
- `bench` (vram/encoder) и `selftest` всегда идут с `cache_supersede=none`: замер и проверка —
  не обслуживание кэша, они не вытесняют и не удаляют ни одной записи;
- `cache/models/fp8_transformer*` не чистится никогда (пересборка = 26 s каста + 6.7 ГБ записи).

Требования к CLI: `--help` у каждой подкоманды, значения по умолчанию = проверенные (см. §4),
никаких интерактивных подтверждений для read-only операций, удаление — только с явным флагом.

Логи прогона: `run` кладёт отладочный лог в подпапку кадра — `<кадр>/run.log` +
`<кадр>/meta.json` (папка = путь кадра без расширения, `qwenstyle/runlog.py`), а `gen` — один
`run.log` + `meta.json` в корне папки сессии `out/<имя>/gen-<штамп>/`. Выключается `--no-logs`
(или `logs: false` в пресете). Лог — наблюдение: ключ кэша эмбеддингов и кадр от него не зависят,
ошибка записи не роняет прогон;
`bench`/`selftest`/тесты ходят в `pipeline.run(..., log=None)` и папок не оставляют. Тесты
пишут результаты только в `out/tests/`, а промт берут из `tests/texts/exp1.txt` (не из `prompts/`,
он в `.gitignore`).
Вся новая логика добавляется в подкоманду (`qwenstyle/cmd/<name>.py`), а не в ядро; монолиты
`run_style.py`/`upscale.py`/`colorfix.py`/`tools/*.py` удалены на шаге 11 переезда (git в
репозитории нет — восстановить нельзя, поэтому добавление возможностей идёт только в пакет).

### R3. Сначала кэш, потом сеть, потом вычисления

Порядок действий при любом запуске: проверить локальный кэш вычислений → проверить `hf-cache/`
(оффлайн) → только потом сеть (`HF_HUB_OFFLINE=0`). Скрипт по умолчанию работает оффлайн;
это осознанное решение, ломать его нельзя.

### R4. Не менять раскладку памяти без замеров

Любая правка `--fp8`, `.to("cuda")`, `enable_layerwise_casting`, `enable_model_cpu_offload`
сопровождается замером: время фазы, VRAM, RSS. Уже проверенные цифры — в §4; если они
изменились, обновлять §4 в этом файле.

### R5. Windows-специфика не «исправляется» наугад

Симлинки требуют admin/Developer Mode; без них `huggingface_hub` деградирует cache
(переносит файл из `blobs/` в `snapshots/`). Раскладка уже приведена к канонической —
если создаёшь/переносишь файлы в `hf-cache/`, сохраняй схему `blobs/<etag>` + относительный
симлинк `../../blobs/<etag>`.

### R6. Новая модель = модуль бэкенда + пресет (ядро не правится)

Подстановка модели генерации, апскейла или текст-энкодера не трогает `pipeline.py`/`cli.py`:

1. `qwenstyle/backends/<name>.py` с `@register_generation` / `@register_upscale` / `@register_encoder`,
   а также `caps: Capabilities` и `budget: ResourceBudget` (контракты — `qwenstyle/backends/base.py`).
   Conditioning объявляется честно: `precomputed` (сами считаем `.pt`), `internal` (промт и
   референсы уходят в пайплайн, как у FLUX.2), `image_inputs` — `none|single|multi`.
2. `qwenstyle/presets/<name>.yaml` — только данные: `extends: base`, `generation.backend: <name>`,
   `encoder.name`, `upscale.backend`, шаги/точность/`precision_cache`.
3. Проверка **без скачивания**: `python -m qwenstyle models list` (caps/budget в строке) и
   `python -m qwenstyle models probe <repo> --offline` (компоненты + вердикт по 16 GiB VRAM /
   63.6 GiB RAM / свободному диску).
4. Прогон: `python -m qwenstyle run --config <name> --dry-run …` (план без весов: сетка, ключ кэша,
   нужен ли энкодер), затем без `--dry-run`. Кэш эмбеддингов ключуется через `RunConfig`
   (`cache_key_parts`/`embeds_key`), поэтому новая модель получает свой тег автоматически.

Нужен ли модели референс — объявляется **только** в `Capabilities`: `requires_image` (по умолчанию
`True`, т.е. прежнее поведение) и `image_inputs` (`none|single|multi` — сколько референсов
принимает `generate`). Ядро читает `requires_image` в `pipeline.input_problem()` и падает **до**
загрузки весов строкой `модель <backend> требует референс: передайте --input <png>` (exit 2, без
трейсбека) — списка имён моделей в ядре нет. `requires_image=False` разрешает T2I, но тогда
пропорцию кадра обязан задать `--aspect` (без него — `1:1`), а в ключ кэша эмбеддингов вместо
sha256 картинки попадает сегмент `noref` (`io.NOREF_SHA`).

## 3. Что и почему кэшируется сейчас

Пути в таблице записаны до миграции шага 4 (кеши разделены): `cache/fp8_transformer*` →
`cache/models/fp8_transformer*`, `cache/weights/…` → `cache/models/weights/…`, `cache/embeds_*` и
`cache/text_embeds_*` → `cache/embeds/`. Ключи и содержимое записей не менялись.

| Кэш | Где | Что экономит |
|---|---|---|
| Веса модели и LoRA | `hf-cache/hub/...` (32 GiB, `blobs/` + относительные симлинки) | 31 GiB + 419 MiB загрузки + запросы к Hub |
| fp8-трансформер | `cache/fp8_transformer/` (base) и `cache/fp8_transformer_turbo/` (turbo) — по 6.7 GiB | каст 26 с + чтение 14.2 ГБ вместо 6.7: старт 36.5 s → ~4 s |
| Эмбеддинги промта и картинки | `cache/embeds_<md5(prompt)[:12]>_<sha256(image)[:12]>[_te-<энкодер>][-<dtype>][-dev-<device>]_<W>x<H>.pt` + `.json` (6.5 МБ @640, 11.6 МБ @1024); сегмент `-dev-cuda` появляется на GPU-пути (умолчание `auto` на машине с CUDA), `bfloat16`/`cpu` без сегмента | **35 с cold / 6 с warm** GPU-энкода (умолчание); 55 с @864×480 и 255 с @1376×768 — только при `--set encoder.device=cpu` |
| fp8-трансформер H3 (33B) | `cache/fp8_transformer_h3_image/` — 30.93 GiB, 17 шардов + `index.json`/`precision.json` | каст 61.7 GiB bf16 однократно **202.8 s** + запись; чтение 0.4–0.6 s вместо десятков минут |
| Веса энкодера 32B | `cache/models/weights/h3qwen32-heretic/` — 62.13 GiB bf16, **3 шарда** < 40 GiB (23.79/23.86/14.49 GiB); читаются **позиционно** (`seek+readinto` по своему разбору заголовка safetensors, `qwenstyle/shards.py`, без mmap и без `safetensors`) | в RAM целиком не поднимаются (только `stream=true` по модулям, загрузка 0.4 s); commit не растёт на размер шардов: было `safe_open` **+62.37 GiB** на три шарда, стало **+0.00 GiB**; дробление шардов — обход бага safetensors (D12, для энкодера больше не нужен) |
| Эмбеддинги H3 (`text_embeds`) | `cache/text_embeds_<md5(prompt)[:12]>_<sha256(image)[:12]|**noref**>_te-h3qwen32-heretic-dev-cuda_<W>x<H>.pt` + `.json` — hidden state **после 50-го слоя** (hidden 5120), `(1,N,5120)` | **118.9 s** cold на GPU (218 токенов T2I) / 82.8 s (1249 токенов edit) → 0 s из кэша; `peak_uss` 5.25 GiB, `peak_vram` 1.93 GiB |
| Сам text-encoder (17.5 ГБ) | не грузится вовсе при попадании в кэш эмбеддингов | ~5 с чтения + RSS 17.6 → 1.4 GiB на CPU-пути; на GPU-пути в RAM не поднимается (стриминг по модулям) |

Не кэшируется и это осознанно: латенты VAE, шаги сэмплера, сам результат генерации
(см. §7 про то, что даётся бесплатно, а что стоит энкода).

**Текст-энкодер считается на GPU по умолчанию** (`encoder.device: auto` в `presets/base.yaml`):
при доступной CUDA `auto` разрешается в `cuda` и сам включает стриминг весов (`stream=True`,
`prefetch=4`), поэтому в VRAM живёт один модуль (пик VRAM ~1 GiB, 3.5 GiB на промте в 4128
токенов; `peak_uss` ~4.7 GiB), а веса не поднимаются в RAM целиком. После энкода VRAM и открытые шарды освобождаются
(`text_encoder=None`), в шагах сэмплера энкодер не участвует. На CPU энкод идёт только явным
`--set encoder.device=cpu` (55 с @864×480 … 255 с @1376×768, RSS 17.6 GiB) и пишет запись кэша
без сегмента `-dev-cuda`.

Энкодер больше RAM читается по слоям с диска (`--set encoder.stream=true`, §4): веса не поднимаются
в память целиком, но ключ кэша эмбеддингов при этом не меняется — записи не пересоздаются. То же и
для GPU-режима (`--set encoder.device=cuda --set encoder.prefetch=4` — он же умолчание на машине
с CUDA): в VRAM живёт один модуль, ключ тот же, а устройство энкода уже отражено сегментом
`-dev-cuda`. Уборка устаревших записей — только отложенная задача `cache_supersede` в конце
`run`/`gen` (R2), никогда во время энкода.

Для `h3-image` тот же `streaming.py` читает **Qwen3-VL-32B** (62.13 GiB) из
`cache/models/weights/h3qwen32-heretic` позиционным чтением (`qwenstyle/shards.py`: заголовок
разбирается сам, байты тензора — `seek+readinto`, mmap нет), но фаза энкодера идёт
**отдельным процессом** (`encode() → _encode_in_child`): `precision.load_cached` держит ~2× размер
fp8 (+64.8 GiB под 30.9 GiB) и по-прежнему на `safe_open`, поэтому commit дочернего процесса умирает
вместе с ним, а fp8-трансформер грузится отложенно в `generate` (§4, грабли H3).

## 4. Проверенные ограничения и цифры

**Память.** Модель 30.86 GiB (23 файла) в bf16 в 16 ГБ не влезает. Раскладка: transformer
14.2 ГБ bf16 → 6.6 ГБ fp8 на GPU; text_encoder 17.5 ГБ — стримингом на GPU (пик VRAM ~1 GiB)
и только при промахе кэша эмбеддингов, после энкода освобождается; на CPU он считается только
с `--set encoder.device=cpu`; VAE 1.35 ГБ на GPU (slicing+tiling); LoRA 420 МБ.
VRAM после загрузки: **9.0/16.0 GiB**; RSS **1.4 GiB** на быстром пути (без text-encoder),
17.6 GiB — только при CPU-энкоде.

**Размеры кадра: `p` = просто высота кадра в пикселях** (864×480 = 480p, 1536×864 = 864p,
1696×960 = 960p, 1920×1088 = 1088p). `--size NNNp` задаёт высоту, а `--resolution`
(= `sqrt(площадь crop)` = `H * sqrt(ratio)`) считается из неё автоматически по пропорциям входа;
`--resolution` остаётся для совместимости. `--size 480p` и ниже также включает 8 шагов, как `--preview`.
`--aspect 16:9|4:3|1:1` подменяет пропорцию кадра (по умолчанию — пропорция входа): при 1440p
это 2560×1440 / 1920×1440 / 1440×1440, референс подгоняется `fit_cover` (scale-to-cover +
центральный кроп). Аспект входит в ключ кэша через `crop`, поэтому его смена = новый энкод
(6–35 с на GPU, 55–255 с на CPU).

| `--size` | `--resolution` (при 16:9) | crop | токенов | статус / замер (4080) |
|---|---|---|---|---|
| **480p** | 640 | 864×480 | 1728 | черновик: 8 шагов ≈ 6 с, пик 11.2 GiB |
| **768p** | 1024 (default) | 1376×768 | 4128 | финал: 25 шагов ≈ 36–44 с, пик 15.5–15.8 GiB |
| **864p** | 1152 | 1536×864 | 5184 | не замерялось (вероятно без offload впритык) |
| **960p** | 1280 | 1696×960 | 6360 | только с `--offload group`: 25 шагов ≈ **66 с**, пик **10.8 GiB**; без offload = OOM |
| **1080p** | 1251 (ratio 1.342) | 1440×1088 | 6120 | `full-qwen`: 25 шагов **66–67 s**, плато **2.41–2.43 s/шаг** (среднее 2.52), `[done] total 75 s` без поста; пик процесса ≈**9.6 GiB** (nvidia-smi 11.14) — спилла нет |
| **1088p** | ~1440 | 1920×1088 | 8160 | `--offload group`, ожидается ~13 GiB (не замерено) |
| **1440p** | ~1663 | 1920×1440 | 10800 | нативно: **16–17 s/шаг** (25 шагов ≈ 7 мин), `free=0` → спилл активаций; до исправления было **73.9 s/шаг** (см. ниже) |

**Почему 1440p раньше шёл 74 s/шаг** (`out/bench/1440p-diag.md`). Причина не в VRAM и не в
attention: спилл активаций (`free=0` на 10800 токенах) стоит ×2 (16–17 s/шаг), а остальное давало
**давление на RAM** — резидентный CPU-энкодер (17.5 GiB) вытеснял page cache fp8-весов, которые
стримятся с диска на каждом шаге. В контролируемом тесте (тот же 1440p, но снаружи удерживается
34 GiB RAM) получено **70 s/шаг** при идентичных VRAM-пиках, то есть профиль исходных 73.9 s/шаг
(1891 s на 25 шагов) воспроизводится «нажатием RAM». С GPU-энкодом по умолчанию эта причина снята.
Гранулярность `offload_blocks` 1 vs 8 даёт **≤4 %** (20.7 → 19.9 s/шаг, пики VRAM те же), поэтому
`--offload-blocks auto` осознанно не вводился: рычаг не в группе блоков, а в активациях и в RAM.

Цифра **4.1 s/шаг** для 1080p — из диагностики по **2 шагам**: там первый шаг (5.5–5.7 s) весит
половину. На 25 шагах плато **2.41–2.43 s/шаг** (**≈2.4 s/шаг**), среднее 2.52 — это и есть
рабочая цифра 1080p.

Для другого соотношения сторон числа `--resolution` другие: например у кадра 1.05 «768p»
даёт `--resolution 788` и crop 832×768 (высота всё равно 768). Фактический размер всегда виден в логе:
`[size] 768p при ratio 1.052 -> --resolution 788` и `[in] … -> conditioning WxH`.

**Режим `--offload group` (для 960p и выше).** Блоки трансформера остаются в fp8 на CPU и
стримятся на GPU по одной группе (`num_blocks_per_group`), поэтому веса в VRAM — ~0.2 GiB
вместо 6.6. Замеры (4080, 25 шагов, seed фиксирован):

| прогон | пик VRAM | время генерации | скорость |
|---|---|---|---|
| 768p (1024), без offload | 15.5–15.8 GiB | 36–44 с | 1× |
| 768p (1024), `--offload group` (blocks 1) | 8.0 GiB | 97 с | ~2.2–2.7× медленнее |
| 768p (1024), `--offload group` (blocks 4) | 8.0 GiB | 83 с | ~2× |
| 960p (1280), `--offload group` (blocks 1 / 8 / 16) | **10.8 GiB** | **66–67 с** | ~1.5–1.8× медленнее 768p |

- Результат **бит-в-бит** совпадает с прогоном без offload (max diff 0 на 1024), то есть режим
  меняет только раскладку памяти, а не картинку.
- `--offload-blocks` на 1280 не влияет ни на VRAM (активации доминируют), ни на время: достаточно `1`.
- Флаги: `--offload {none,group}`, `--offload-blocks N` (по умолчанию 1), `--offload-stream 0|1` (по умолчанию 1).
- На Windows первый кадр после старта может быть в 2–3 раза медленнее последующих (WDDM-пейджинг,
  когда рабочий стол держит 2–3 GiB): это не ошибка режима, а тот же эффект, что и без offload.

**Старт и прогон (замер, прогретый page cache, оффлайн):**

| время | фаза |
|---|---|
| 0.7 s | pipeline с fp8-трансформером из кэша, без text-encoder (+~2 s `.to("cuda")`) |
| 0.5 s | `load_lora_weights` + `set_adapters` + 448 тензоров fp8 → bf16 |
| 25.8 s + 14.0 s | однократно: bf16 → fp8 каст + запись `cache/fp8_transformer` |
| **35 s cold / 6 s warm / 0 s** | **энкод промта на GPU** (умолчание `encoder.device=auto`): 35 s cold — 1283 токена @640×480, 6 s warm — 2513 токенов @1440×1088, 0 s — попадание в кэш эмбеддингов |
| 55 s / 255 s | CPU-энкод Qwen3VL-8B на 864×480 / 1376×768 — только при `--set encoder.device=cpu` |
| 6 s / 38 s | генерация: 8 шагов @640 / 25 шагов @1024 |
| **11 s** | полный прогон `--preview` после прогрева обоих кэшей |
| ~350 s | первый прогон @1024 с CPU-энкодом (`--set encoder.device=cpu`); с GPU-энкодом энкод стоит 6–35 s |

Итог: с GPU-энкодом (умолчание) холодный прогон уже не упирается в энкод (6–35 s) — время съедают
шаги сэмплера; доминирует CPU-энкод (55–255 с) только при `--set encoder.device=cpu`, а после
прогрева кэша эмбеддингов всё упирается в шаги в обоих случаях.

**Из чего состоит пик VRAM** (замер `python -m qwenstyle bench vram`, 4080, fp8, LoRA 0.7, эмбеддинги из кэша):

| статья | @640 (864×480, 1728 токенов) | @1024 (1376×768, 4128 токенов) |
|---|---|---|
| веса после загрузки (`allocated`) | 7.67 GiB | 7.67 GiB |
| **активации** (пик денойзинга − веса) | **1.59 GiB** | **3.63 GiB** |
| резерв аллокатора (reserved − peak allocated) | 0.62 GiB | 1.55 GiB |
| вне аллокатора torch (контекст CUDA, библиотеки) | 1.33 GiB | 2.62 GiB |
| **пик по процессу** | **11.2 GiB** | **15.5 GiB** |
| VAE-декод (bf16, tiled+sliced) | 0.45 s, пик 9.1 GiB | 0.99 s, пик 10.3 GiB — **меньше** денойзинга |
| forward трансформера | — | 25 × 1.33 s = 34.6 s (**95 % прогона**) |

Что из этого следует для оптимизаций (проверено, а не гипотеза):
- активации — **не** 8–9 GiB, как можно было предположить по дельте пика: 3.63 GiB @1024; главное — веса 7.67 и фиксированные накладные 2.62+1.55 GiB;
- `PYTORCH_CUDA_ALLOC_CONF=max_split_size_mb:256` **ничего не даёт** (15.548 vs 15.505 GiB) — не крутить;
- VAE уже bf16, а декод дешевле денойзинга → «декод в bf16» и «освободить трансформер перед декодом» бесполезны;
- единственный содержательный рычаг для >1024 — вывести веса из VRAM (`--offload group`): он снимает
  6.6 GiB и делает 1280 рабочим (10.8 GiB, см. таблицу выше);
- время прогона — это чистый forward (1.33 s/шаг @1024); `scheduler.step` и VAE-энкод (0.66 s) в балансе не значат ничего.

**Диск-стриминг текст-энкодера (`--set encoder.stream=true`).** Модель собирается на meta-параметрах
(`accelerate.init_empty_weights(include_buffers=False)`, буферы вроде `rotary_emb.inv_freq` живые) и
грузит веса каждого модуля перед его forward позиционным чтением (`seek+readinto` без mmap,
`qwenstyle/shards.py`), освобождая после; код —
`qwenstyle/streaming.py`. Это снимает требование «энкодер ≤ RAM»: 32B в bf16 (62 GiB) целиком
в 63.6 GiB не влезает вместе с активациями. Замер на реальных весах (FLUX.2-энкодер
`Qwen3ForCausalLM`, 15.26 GiB, 8.19B, 399 тензоров, 16 токенов, CPU):

```bash
python -m qwenstyle bench encoder --repo <repo> --subfolder text_encoder --tokens 16 --stream 0 --save cache/_bench/te_full.pt
python -m qwenstyle bench encoder --repo <repo> --subfolder text_encoder --tokens 16 --stream 1 --compare cache/_bench/te_full.pt
```

| прогон | загрузка | forward | peak_uss | peak_rss |
|---|---|---|---|---|
| stream 0 | 16.1 s | 5.8 s | **15.91 GiB** | 15.93 GiB |
| stream 1 | 0.2 s | 8.4 s | **1.75 GiB** | 17.10 GiB |

- Результат **бит-в-бит**: `[diff] layer=9/18/27 max=0.0` — стриминг меняет раскладку памяти,
  а не арифметику. Ключ кэша эмбеддингов при `stream=True/False` не меняется (тест сверяет и имя
  файла, и `cache_key_parts`), записи не пересоздаются.
- Главная метрика — **`uss`** (`psutil.memory_full_info()`): mmap-страницы попадают в `rss` и дают
  ложное «не помогло» (`peak_rss` во втором прогоне выше — 17.10 против 15.93), а приватная память
  падает на 14.17 GiB (~9×).
- Цена — чтение весов с диска на каждом forward (8.4 s против 5.8 s на 16 токенах); загрузка
  наоборот почти бесплатна (0.2 s против 16.1 s).
- Диск-стриминг **включён по умолчанию на GPU-пути**: `encoder.device: auto` на машине с CUDA сам
  ставит `stream=True`/`prefetch=4` (§3). Для `encoder.name=base` (Qwen-Image-2.1) веса Qwen3VL-8B
  тоже грузит этот загрузчик — `streaming.load_text_encoder(..., device="cuda")`, вместе
  с vision-башней (16.33 GiB в том же наборе); предупреждения «веса грузит diffusers, режим
  пропущен» больше нет. С `--set encoder.device=cpu` работает прежнее умолчание поля
  (`stream=False`) и старый CPU-путь; внешние энкодеры (FLUX.2, heretic-te, `encoder.local_dir`)
  идут через тот же код.
- **Проверка на 4-шардовых весах heretic-te** (`cache/weights/heretic-te`, 750 тензоров, 16.33 GiB,
  8 токенов, `bench encoder --local-dir`): `stream 0` — загрузка 44.4 s, forward 4.1 s,
  **peak_uss 16.93 GiB**; `stream 1` — загрузка 0.1 s, forward 5.6 s, **peak_uss 1.75 GiB**
  (−15.19 GiB, ~9.7×), `[diff] layer=9/18/27 max=0.0` → бит-в-бит и на реальном 4-шардовом наборе
  (`out/bench/te-stream-heretic.md`). Оговорки: `stream=True` работает на `device='cpu'` и `cuda`
  (с шага «GPU-стриминг», §4 ниже); post-hook зарегистрирован с `always_call=True`, поэтому при
  исключении в forward веса модуля всё равно освобождаются, а дескрипторы шардов закрываются при ошибке
  (`ShardedWeights.close()`); строка `[stream] N параметров пришли с requires_grad=True -> снят`
  в логе — норма (стриминг только для инференса).

**GPU-стриминг энкодера (RAM-стейджинг + конвейер).** Тот же `qwenstyle/streaming.py`, но веса
модулей читаются с диска в pinned-буфер RAM фоновым потоком и асинхронно копируются в VRAM
(`--set encoder.stream=true --set encoder.device=cuda --set encoder.prefetch=4
[--set encoder.pin_memory=0] [--set encoder.lookahead=N]`), в VRAM живёт только текущий модуль.
Источник чисел — `out/bench/te-gpu-stream.md` (шаг 5 плана `te-gpu-streaming`), энкодер
`Qwen3ForCausalLM` 8.19B / 15.26 GiB bf16, `HF_HUB_OFFLINE=1`.

Плечи (`python -m qwenstyle bench io --read-gib 4 --h2d-gib 0.5`):

| плечо | GB/s | вывод |
|---|---|---|
| NVMe → RAM, проход 1 (условно «холодный») | **4.39** | нижняя граница диска; page cache не сбрасывается, поэтому это не честный cold |
| NVMe → RAM, проход 2 (тёплый, page cache) | **6.81** | именно этот режим работает для 8B: модель влезает в 63.6 GiB RAM |
| RAM → VRAM, pinned | **26.70** | H2D не предел: 15.26 GiB = ~0.6 s |
| RAM → VRAM, pageable | **20.50** | выигрыш pinned = **1.30×** — на этом профиле pin покупает RAM (≈2.4 GiB `peak_uss`), а не время |

**Pinned staging и group-offload — конфликт (решён в коде).** На Windows pinned-память CUDA — это
блокировка страниц **и** маппинг в адресное пространство GPU (WDDM), то есть тот же ресурс, что и
VRAM. Групповой offload держит в pinned-памяти 6.6–8.5 GiB весов fp8-трансформера, после чего
первый же крупный staging-буфер энкодера падал прежде, чем начинался forward:

```
[4/5] кодирование промта на GPU (Qwen3VL-8B, стриминг)...
torch.AcceleratorError: CUDA error: out of memory   # streaming.py: torch.empty(..., pin_memory=True)
# повторный запуск, без ручных флагов:  [done] … 974x1440, total 76s
```

Поэтому `RunConfig.encoder_pin_memory` выключает pin **принудительно** при `generation.offload=group`
(`--set encoder.pin_memory=1` его не включает), а `_PinnedPool` дополнительно деградирует, если
pinned-буфер всё же не выделился. Цена: H2D 20.5 вместо 26.7 GB/s, то есть 0.05–0.31 s из 8–10 s
энкода (§4 ниже) — замена упавшему прогону. Замер после правки: `full-qwen` 1088p с нуля,
без `--set`: энкод 16.33 GiB стримится с `pin_memory=0`, полный прогон **76 s**.

Прогоны (`bench encoder --stream 1`, forward = стена, в скобках — `compute` из `[stream]`):

| tokens | CPU `stream=1` | GPU `prefetch=4` | ускорение (стена) | peak_vram | peak_uss |
|---|---|---|---|---|---|
| 16 | **13.1 s** И (compute 6.38) | **10.3 s** И (compute 0.27) | **1.27×** И | 1.18 GiB И | 4.80 GiB И |
| 512 | **97.6 s** И (compute 88.27) | **10.4 s** И (compute 0.28) | **9.4×** И | 1.46 GiB И | 4.72 GiB И |
| 4128 (реальный промт @1376×768) | ~787 s **ОЦЕНКА** (линейно от 512 токенов; CPU-прогон не запускался) | **10.5 s** И (compute 0.81) | **~75× ОЦЕНКА** | 3.50 GiB И | 4.83 GiB И |

- И/О = измерено/оценено. CPU-прогон на 4128 токенах сознательно не запускался: ~13 мин ничего
  не меняют в выводе, а GPU-число — прямое измерение. Даже если взять известные 255 s CPU-энкода
  проекта (без диск-стриминга), нижняя граница выигрыша — **~24×** (255 / 10.5).
- **Численность:** `max|diff|` prefetch 0 vs 4 = **0.0** на слоях 9/18/27 → конвейер — раскладка,
  а не другая математика. CPU vs GPU = **128.0** (шаг квантования bf16 на больших активациях) →
  `encoder.device` обязан быть в ключе кэша (R1), иначе один `.pt` означал бы два разных тензора.
- **I/O-bound, а не compute-bound:** GPU-время почти не зависит от длины промта
  (10.3 / 10.4 / 10.5 s на 16 / 512 / 4128 токенов), ожидание данных — **0.92–0.97** бюджета,
  read 7.7–8.44 s, copy 0.05–0.31 s, compute 0.27–0.81 s. Растёт только VRAM активаций
  (1.18 → 1.46 → 3.50 GiB), `peak_uss` стоит на 4.72–4.83 GiB.
- **Память по прогонам GPU** (`bench encoder`, 16 токенов): `prefetch 0` — `peak_uss` **2.43** GiB /
  `peak_vram` **1.18**; `prefetch 4` (pin) — **4.80** / **1.18**; `prefetch 4 --no-pin` — **7.18** /
  **1.19**; на 512/4128 токенах — `peak_uss` **4.72**/**4.83** при `peak_vram` **1.46**/**3.50** GiB.
- **Где предел:** на прежнем mmap-пути фактическое чтение по модулям шло со скоростью **1.7–1.9 GB/s**
  против 4.4–6.8 GB/s последовательного (`bench io`) — виновата была гранулярность mmap по 399 тензорам,
  а не диск, не H2D (26.7 GB/s) и не compute (0.27 s). После перевода на позиционное чтение (§4 ниже)
  эти числа **не перемерялись** (D8); кэш fp8 лечит симптом (объём), а не причину.
- `ratio_wait` в `[stream]`-сводке считает только `Event.wait()` и на конвейере равен 0.00 —
  I/O-bound читается по строке `budget` (ожидание данных) и по `read` vs `compute`, не по нему.
- Умолчание — `device=auto`: на машине с CUDA это `cuda` + `stream=True` + `prefetch=4`
  (+`pin_memory=True`, `lookahead=1`), на машине без CUDA — прежние `cpu`/`stream=False`/`prefetch=0`.
  Откат на CPU-путь — `--set encoder.device=cpu`. Ключ кэша конвейер не трогает
  (только `device`/`dtype` — сегментами имени).
- **Вердикт по fp8-кэшу энкодера:** для 8B — **не нужен** (read доминирует, ожидаемая экономия
  < 2×, модель и так влезает в page cache); для 32B (62.1 GiB в 63.6 GiB RAM с активациями
  не влезает) — **нужен**, но вводить только после замера (D9). Код fp8-энкодера не писался.

**Чтение весов энкодера: позиционный `seek+readinto` (`qwenstyle/shards.py`).** `ShardedWeights`
больше не ходит в `safetensors`/mmap: заголовок шарда разбирается своим кодом, байты тензора читаются
`seek + readinto` под замком — и в обычный буфер, и прямо в pinned-буфер конвейера
(`_PinnedPool.reserve`). Источник чисел — `out/bench/shards-readinto.md`; байты бит-в-бит
(`torch.equal` на реальных весах шага 2).
- **commit:** `safe_open` трёх шардов 32B = **+62.37 GiB** (23.88 / 23.95 / 14.54 GiB на каждый, без единого
  прочитанного тензора), `ShardSet` + `file_dtypes()` = **+0.00 GiB** (как и `open()`); `read` одного
  тензора — ровно его байты (+1.46 GiB за 1.45 GiB `lm_head.weight`). Открытие шарда **2.3–3.3 ms**
  против 1.39 s у `safe_open`.
- **Скорость:** холодное плечо без регресса (old **2.53** / new **2.58** / new-pinned **2.66** GiB/s —
  все упираются в диск), но тёплое у нового пути **медленнее**: old **19.45–21.24** против new
  **6.51–7.13** GiB/s, потому что mmap-слайс+`clone` — один memcpy из page cache, а `readinto` —
  копия через syscall. Оставшийся рычаг — `mmap.mmap` самого файла (commit-free, замер **+0.09 GiB**).
- **Коалесить не нужно:** слой 0 (930.02 MiB, дыр 0 байт) — 11×`read_into` **8.90** GiB/s против
  одного чтения диапазона **8.56** GiB/s (в пределах шума).
- **Фаза `[3/4]` (`h3-image --size 480p --aspect 1:1`):** `ok, 58.6s prompt_embeds (1, 453, 5120)`,
  процесс фазы 65.9 s, `[done] total 123s`, фоллбек не понадобился; плато фазы **56.75–57.03 GiB**
  commit (**+15.3** к baseline 41.60 GiB — это дельта commit **дочернего процесса фазы** от baseline,
  снятого в родителе до его старта, то есть вместе с самим процессом, а не только с чтением;
  pinned-пул ограничен, пиковая занятость `peak_uss=4.37 GiB`), а пик всего прогона **114.70 GiB**
  (лимит 111.51, Windows расширил pagefile до 117.37) даёт **fp8-кэш** (`qwenstyle/precision.py`),
  не энкодер; `bench encoder` на всех 62.13 GiB — `read=68.99 s`, пик commit **+14.45 GiB**
  (та же природа дельты).

**Проверки корректности (не ломать при доработках):**
- Генерация детерминирована: два прогона с одним `--seed` дают max diff 0.
- Эталонные кадры и команда сверки (parity) удалены в v0.1.0: сверка нового каркаса со старыми
  монолитами была завершена до их удаления. Штатная проверка установки теперь —
  `python -m qwenstyle selftest --profile <имя>` (окружение → веса профиля → один рендер 480p/4 шага),
  проверка доступа к весам — `models download --profile … --probe`.
- Старт из `cache/models/fp8_transformer` даёт **бит-в-бит** тот же кадр, что inline-каст bf16→fp8 (max diff 0).
- Поэтому при загрузке fp8-кэша `from_pretrained(dtype=fp8)` нельзя применять «как есть»: он кастит ВСЁ, включая 67 не-fp8 тензоров (32.5 MiB — нормы, patch/pos-embed, proj_in/out), а буферы `persistent=False` (синусоидальные `freqs`) в файл весов не попадают вообще. Не-fp8 тензоры читаются с диска точно, буферы — из sidecar; без этого forward падает с `Promotion for Float8 Types is not supported` или картинка меняется целиком.

`--upscale-backend esrgan` (по умолчанию) — Real-ESRGAN x4plus_anime_6B:

| генерация, кадры 2–8 | **~39.8 s** каждый (батч из 8 seed'ов — 327 s) |
| полный тёплый прогон | `[done] total 264 s` (энкод 127.5 + генерация 101.8), PNG 1088×1024 ≈ 1.9–2.0 МБ |

Вывод: 1024² не только влезает (VRAM 7.5 GiB из 16), но и вдвое предсказуемее 512×512 по восприятию:
кадры сравнивать сериями, пересчитывая только энкод разрешения.

Грабли (важно для будущих работ):
- `safetensors` 0.8.0 на Windows падает access violation на `get_tensor` из файлов ≥ ~40 GiB
  (синтетика: 39 GiB ок, 40 → segfault) → веса энкодера пересобраны в 3 шарда < 40 GiB
  в `cache/models/weights/h3qwen32-heretic` (23.79/23.86/14.49 GiB). Для энкодера это больше не
  обязательно (его шарды читаются своим кодом, без `safetensors`), но `precision.py` и другие
  `safe_open` остаются (D12).
- На этой машине mmap файла списывается в commit целиком: `safe_open` трёх шардов энкодера был
  **+62 GiB commit** при rss 0.4 GiB, теперь шарды читаются без mmap и стоят **+0.00 GiB** (см. §4
  выше), а `precision.load_cached` держит **+64.8 GiB** под 30.9 GiB fp8 → фаза энкодера
  идёт **отдельным процессом**, её commit умирает вместе с ним, а fp8-трансформер грузится
  отложенно в `generate` (§3).
- Холодная фаза энкодера была хрупкой: 4 из 8 попыток за день упали на pinned-аллокации
  (`CUDA error: resource already mapped`); после перевода шардов на позиционное чтение такого нет
  (§4, D10), но фоллбек с одной повторной попыткой (`_sync_encoder_cfg`) и внятным `RuntimeError`
  вместо молчаливого AV оставлен страховкой.
- `1024²` (умолчание пресета `size_px: 1024`) **замерен**: 1088×1024, edit — энкод 32B 127.5 s
  (2311 токенов), генерация 101.8 s / **~39.8 s** тёплых, peak-ish VRAM **7.5 GiB** (см. таблицу выше).
- warning diffusers про `unexecuted_layers=['pdd_proj_out.{1..5}']` — норма (lazy-prefetch trace),
  на кадр не влияет; `offload_stream=0` его убирает, но стоит 2.7× по времени (92.6 s против 34.7 s).

**Прочие ограничения:**
- `addmm` для fp8 в torch не реализован → LoRA-тензоры (448 шт.) после загрузки кастуются в bf16, иначе падение на первом шаге.
- `true_cfg_scale` в 2.1 по умолчанию 1.0 → `negative_prompt` игнорируется, CFG-ветки нет.
- `QwenImage21Pipeline.__call__` не принимает `image_pad_mask`, а с `image`+`prompt_embeds` падает → `encode_prompt` подменяется замыканием на готовые эмбеддинги. При обновлении diffusers это место проверять первым.
- `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` на Windows не поддерживается (torch пишет warning) — фрагментацию не лечит; для 1280 вместо этого `--offload group`.
- `torch_dtype=` в diffusers 0.43 — deprecated, но актуальный аргумент; на `dtype=` переходить только вместе с проверкой версии.
- Каст в fp8 по построению идёт на CPU (модель ещё не на GPU). Обратный порядок потребует 14.2 ГБ bf16 в VRAM (16 ГБ всего) → OOM; поэтому вместо каста на GPU — дисковый кэш `cache/fp8_transformer`.
- `--fp8 0` (bf16-трансформер) = 14.2 ГБ в VRAM вместе с VAE → не влезает, только для экспериментов на другой карте.
- Ловушки при переносе fp8-кэша на другую машину/версию diffusers: пересобрать `--rebuild-fp8-cache` (структура модулей может измениться).
- `hf cache verify MicksHF/Qwen-Image-2.1-Anime-Fusal` предупреждает «32 remote file(s) are missing locally» — норма: в репо 33 файла, пайплайну нужен один `.safetensors`.
- Предупреждение `You are sending unauthenticated requests to the HF Hub` появляется только в онлайн-режиме (метаданные-запросы без токена), на работу не влияет.
- В оффлайн-режиме `diffusers` печатает `Could not reach the Hub … Will try to load from local cache` — это нормальный путь, не ошибка.
- Text encoder — штатный Qwen3VL-8B, а не Heretic BF16 из LoRA-репозитория (16.3 ГБ в кэше нет): стиль работает, но conditioning не воспроизводит трейн 1:1 (см. модель-карточку в `.pi/skills/fusal-prompt/references/`).

## 5. Как заполнять промт (формат FUSAL)

Сводные правила написания запросов (режимы, скелеты, что в каждом блоке, длина, антипаттерны,
чек-лист, цена правки) вынесены в [`PROMPT_RULES.md`](PROMPT_RULES.md); ниже — краткая версия,
обязательная к соблюдению в этом репозитории.

Эталоны — `prompts/exp1.txt`…`exp4.txt`. Во всех четырёх **набор и порядок разделов идентичны**,
меняется только детализация (1033–2443 символа). Новый промт пишется по этому же скелету.

### 5.1 Скелет

```
fusal style.
[TASK: TEXT_TO_IMAGE]

[Subject] …
[Appearance] …
[Pose] …
[Expression] …
[Composition] …
[Environment] …
[Lighting] …
[Style] …
```

- Первая строка — ровно `fusal style.` (триггер LoRA), до неё ничего.
- Вторая — `[TASK: …]`: `TEXT_TO_IMAGE` или `IMAGE_EDIT` (+ `[Reference guidance]`, см. 5.3).
  Допустимо в одну строку с триггером (`fusal style. [TASK: …]`), как в exp2–exp4.
- Далее строго эти 8 разделов, каждый тегом с новой строки, содержимое — со следующей строки.
  Порядок фиксирован: Subject → Appearance → Pose → Expression → Composition → Environment → Lighting → Style.
- Разделы не пропускать: в примерах есть все восемь; чаще всего забывают `[Expression]`.
- Внутри разделов — связный английский текст без списков, markdown, кавычек и эмодзи.
  По-английски всё, кроме названий-референсов и надписей в кадре (`labeled "ARGENTO"`).

### 5.2 Что писать в каждом разделе

| Раздел | Содержание |
|---|---|
| `[Subject]` | Одно предложение: сколько персонажей (числом словом — `One young woman`, `Two fictional young adult women`), что делает, где. Допустим ракурс съёмки (`viewed from a floor-level low angle`). Одежды, света, стиля здесь нет. |
| `[Appearance]` | Внешность и одежда сверху вниз: волосы (цвет + причёска + аксессуары) → глаза (цвет) → одежда (цвет, материал, крой, длина) → обувь/чулки/перчатки/украшения/детали (маникюр, ленты, заколки). У каждого предмета — цвет. |
| `[Pose]` | Поза по частям тела с направлением относительно кадра: `extends straight diagonally to the bottom-left corner`, `left hand rests flat on the right armrest`. Сильные искажения перспективы называть прямо: `extreme foreshortening`, `sole facing directly into the bottom-center camera lens`. |
| `[Expression]` | Только лицо и взгляд: глаза (прикрыты/широко раскрыты), рот, румянец, куда смотрит и с каким чувством (`looking down at the viewer from above`, `smug, relaxed smile`). |
| `[Composition]` | Тип кадра (`full body`, `medium-full`, `close`), ракурс и наклон (`high-angle`, `dynamic diagonal`), что обрезано, что в переднем плане; объекты-обрамления с позицией (`left`, `bottom-right foreground`). |
| `[Environment]` | Место и предметы: мебель, светильники как объекты, реквизит с количеством и надписями (`two empty stemmed wine glasses`, `bottles labeled "ARGENTO"`), положение в кадре. |
| `[Lighting]` | Источники и их характер: тёплый/холодный, направление, жёсткость; что именно освещено; атмосферные эффекты (`caustics`, `golden dust particles`, `starbursts`); качество теней. |
| `[Style]` | Только техника рендера: линия (`fine brown outlines`, `bold black cel-shaded lineart`), шейдинг (`layered hard cel shadows`, `painterly soft shading`), палитра, блики, резкость фона; при необходимости референс целиком (`2015 TV anime screenshot in the style of Prison School (Kangoku Gakuen, J.C.Staff)`). |

### 5.3 Режим `IMAGE_EDIT` (как в `python -m qwenstyle run`)

```
fusal style.
[TASK: IMAGE_EDIT]

[Reference guidance] …
[Subject] … (и далее те же 8 разделов)
```

- `[Reference guidance]` — **единственное** место, где перечисляются изменения и запреты на изменения:
  `Edit <image1> in place: preserve its composition, camera angle, poses, hairstyles, colors and background layout exactly as in <image1>; change only the rendering to the target anime style described below.`
  Дальше — явный список правок (`Add that …`, `remove the description of any other clothing`, `The boots can stay.`).
- Остальные разделы описывают **итоговый** кадр (каким он должен стать), а не исходник.
- Входное изображение обозначается плейсхолдером `<image1>`.

### 5.4 Чек-лист перед запуском

- [ ] первая строка `fusal style.`, вторая `[TASK: …]`;
- [ ] все 8 разделов на месте, порядок не нарушен;
- [ ] у каждого предмета одежды есть цвет/материал/длина;
- [ ] ракурс указан и согласован с `[Pose]` (поза физически возможна при этом ракурсе);
- [ ] для `IMAGE_EDIT` есть `[Reference guidance]` со списком «что сохранить / что изменить»;
- [ ] ничего не пытаемся запретить снаружи: `negative_prompt` не работает (см. §4), исключения — в скобках внутри раздела: `(no chest cutout)`;
- [ ] длина 1–3 предложения на раздел: exp1 (2177 симв.) — верхняя граница детализации, exp3 (1033) — минимально достаточная; `[Style]` не раздувать повторами.

### 5.5 Промт и кэш

- Ключ кэша эмбеддингов = `md5(промт)[:12] + sha256(входного файла)[:12] + WxH`, рядом лежит `.json`
  с полным набором параметров. Любая правка формулировки или другой входной файл = miss и
  **6–35 с GPU-кодирования** Qwen3VL-8B (35 s cold @640×480, 6 s warm @1440×1088); на CPU
  (`--set encoder.device=cpu`) — 55 с @864×480 … 255 с @1376×768.
- Финальные формулировки держать в `prompts/` и подавать через `--prompt-file`, а не править в скрипте.
- Полный разбор экономики кэша и порядка итераций — §6; правила написания промтов — §5 и
  `.pi/skills/fusal-prompt/SKILL.md` (там же тиры, блоки T2I/I2I, R18-вариант и режимы правки).

### 5.6 Сила LoRA (`--lora-scale`)

Это множитель низкоранговой поправки: `W' = W_base + s · (α/r) · B·A`, где у нашего R80-адаптера
`α/r = 1.0` (rank 80, alpha 80, alpha-less формат). Т.е. `0.0` — чистая база без стиля, `1.0` —
адаптер ровно как обучен, `>1.0` — экстраполяция (не использовать). Это **не** CFG:
`true_cfg_scale` остаётся 1.0, `negative_prompt` по-прежнему не работает.

Затрагивается только трансформер (224 модуля, 448 тензоров), text encoder — нет. Поэтому смена
`--lora-scale` **не инвалидирует кэш эмбеддингов и не меняет VRAM** — это такая же бесплатная ось,
как `--seed` и `--steps` (замер: 4 прогона на 640 — по ~10 с, один и тот же `.pt`).

| Задача | Диапазон |
|---|---|
| Правка картинки (наш режим `IMAGE_EDIT` / инструкции) | **0.65–0.70** |
| Генерация с нуля (`TEXT_TO_IMAGE`, `IDENTITY_*`) | **0.85–1.0** |
| Диагностика: «откуда артефакт» | **0.0** (если баг есть и без LoRA — дело в промте/базе) |
| 0.7 «пережаривает» лица/кожу | 0.3–0.5 |
| Вернуть сатурацию и плотность теней на fp8-базе | 0.75–0.85 |

Свип (≈1 минута на всё, энкод не платится):

```bash
for s in 0.5 0.65 0.7 0.85 1.0; do
  PYTHONIOENCODING=utf-8 .venv/Scripts/python.exe -m qwenstyle run \
      --preview --lora-scale $s --seed 20261113 --out out/sw-$s.png \
      --input out/camp/canyon-edit-640-lora1.0-s777.png --prompt-file prompts/exp3.txt
done
```

Правила свипа:
- сравнивать только при одном `--seed`, одних `--steps` и одной резолюции: при 8 и 25 шагах
  ощущение «сильнее/слабее» съезжает;
- эффект **немонотонный**: замер на 640/8 шагах, seed 20261113 (mean abs diff по RGB к 0.7):
  `0.0 → 21.2`, `0.5 → 14.3`, `1.0 → 18.0` — 0.5 и 1.0 уходят в разные стороны, подбирать глазами;
- на `1.0` первым делом проверять дрейф анатомии и композиции исходника;
- если результат «не в стиле», сначала убедиться, что адаптер применился (в логе
  `LoRA-тензоров переведено в bf16: 448`), а не крутить seed.
- по-слойной настройки у адаптера нет: масштаб глобальный.

## 6. Порядок генерации и экономика кэша

Правило: **дорогие оси менять один раз, дешёвые — сколько угодно.**

| Ось | Что стоит |
|---|---|
| `--seed`, `--steps`, `--lora-scale`, повторный прогон | только GPU: 6 с @640 / 38 с @1024 (turbo: 5 с / 21 с) |
| текст промта, входной файл, `--resolution` | GPU-энкод: 35 с cold @640×480 (1283 токена) / 6 с warm @1440×1088 (2513), 0 с из кэша; CPU — 55 с @864×480, 255 с @1376×768 (только `--set encoder.device=cpu`) |
| `h3-image`: текст промта, вход/`noref`, `--resolution` | 32B-энкод **118.9 s** на новую пару (218 токенов) / 82.8 s (1249), 0 s из кэша; отдельный процесс на фазу, `peak_uss` 5.25 GiB |
| `h3-image`: `--seed`, повторный прогон | только GPU: 19.2–24.5 s на 512² (6 шагов PDD, `--steps` игнорируется) |
| первый старт на машине / `--rebuild-fp8-cache` | 25.8 с каста + 14 с записи, однократно |

Рабочий порядок:

1. Зафиксировать входную картинку (любая замена файла — новый ключ и новый энкод).
2. Собрать композицию/стиль промта на `--preview` (640p, 8 шагов): один энкод 35 с, дальше каждая
   итерация ~11 с. Здесь перебирать промт в 4–5 раз дешевле, чем на 1024.
3. Перебрать `--seed` / `--lora-scale` / `--steps` на том же 640 — бесплатно (кэш тот же).
4. Финал: **один** прогон на 1024 с лучшими параметрами — пенальти энкода (6–35 с на GPU)
   платится один раз, дальше эта резолюция тоже в кэше.
5. Не прыгать 640 ↔ 1024 ↔ 1280 в цикле: каждая резолюция — свой энкод (6–35 с на GPU за новую,
   55–255 с на CPU).
6. Несколько входных картинок с одним промтом — это N энкодов, а не 1: планировать батчами по
   паре (картинка, резолюция) и сравнивать результаты только внутри батча.
7. Очистка: живые эмбеддинги — только те, чьё имя содержит актуальные `md5+sha`; записи старой
   схемы (без хеша картинки) мёртвые. `.json` рядом с `.pt` — единственный способ понять, чем
   запись сгенерирована, без чтения бинаря.

**Порядок итераций для `h3-image`** (тот же принцип, другие числа): шагов ровно 6 (расписание PDD),
и они дешёвые — 19–25 s тёплых на 512²; дорогая ось — энкодер 32B: **118.9 s** на новую пару
(промт, картинка, резолюция) плюс отдельный процесс на фазу.

1. T2I — задать `--aspect` (без него `1:1`) и `--size 512p`, прогнать промт один раз: запись
   `text_embeds_…_noref_te-h3qwen32-heretic…` живёт как обычный кэш, дальше `--seed` бесплатен.
2. Edit — тот же промт и один `--input`; любая правка формулировки или другой файл = новый энкод.
3. Не прыгать 512 ↔ 1024: каждая резолюция — свой энкод (у 1024² edit это 2311 токенов → **127.5 s**),
   но сама генерация там дешёвая: **~39.8 s** тёплых на кадр при VRAM 7.5 GiB — поэтому финалом можно
   сразу брать `size_px: 1024` (умолчание пресета), а 512p держать только для быстрых черновиков.
4. Тёплый цикл — `[done] total 29 s` (T2I) / 34 s (edit) против 96–99 s (T2I с готовым кэшем
   `text_embeds`) и 201 s холодного edit — кадры сравнивать сериями, а не по одному.

**Правило размера финального кадра.** Финал 1440p = рендер **1080p** (1440×1088, 25 шагов
**66–67 s**, `[done] total 75 s`) + ESRGAN ×1.32 до 1906×1440 — это дефолт `full-qwen`
(`size_px: 1080`, `upscale.target_height: 1440`). Нативный 1440p (1920×1440, 10800 токенов) —
**16–17 s/шаг** (25 шагов ≈ 7 мин, ×6.5 к 1080p) из-за спилла активаций: он оправдан только
для узких кадров (<2.2 МП) и при свободной RAM (перед прогоном проверить `RAM available ≈ 49 GiB`,
иначе s/шаг уходит в 70 — см. §4).

Апскейл **пропускается автоматически**, если кадр уже не ниже `upscale.target_height` или фактор
≈ 1: бекенд не загружается, печатается `[post] upscale пропущен: …`, суффикс `-x1` в имени не
появляется. ⚠️ `--upscale 0` **не отменяет** `upscale.target_height` из пресета (фактор считается
из высоты: 1440 / 1088 → ×1.32), поэтому чистый кадр без поста — только с
`--set upscale.target_height=0`.

Серия кадров по seed'ам — `python -m qwenstyle gen --preset strong --prompt <имя> --count 9`
(или `--seeds 0-9`): пайплайн грузится один раз, апскейл — после его выгрузки, имена
`s{N}.png` (+ `s{N}-gen.png` чистая генерация), `run.log` и `meta.json` — в корне папки сессии.
Эмбеддинги `gen` **не создаёт** — при промахе печатает готовую команду `run`.

- **D8. Гранулярность чтения весов энкодера — по пути данных закрыто, по скорости тёплого плеча нет.**
  Данные больше не идут через mmap-связку `safetensors`: шард разбирается своим заголовком, тензор
  читается целиком (`seek + readinto`, 250–930 MiB за вызов, `qwenstyle/shards.py`), и на холодном
  плече это не хуже прежнего mmap (**2.53 → 2.58 GiB/s**, `out/bench/shards-readinto.md`).
  Что осталось: тёплое чтение медленнее прежнего mmap+`clone` (**6.5–8.1** против **19.5–21.2** GiB/s) —
  рычаг `mmap.mmap` самого файла (commit-free, замер +0.09 GiB) или `FILE_FLAG_SEQUENTIAL_SCAN`
  для холодного плеча. Старые числа — **1.7–1.9 GB/s** на модуль и `bench encoder` **205.2 s** на
  512 токенах — **не перемерялись**, ориентировочные; реальное чтение всех 62.13 GiB сейчас
  `read=68.99 s` (≈0.90 GiB/s на 1058 тензорах) — другое измерение (другой файл, другой прогрев).
