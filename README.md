# qwenstyle — NSFW-style: локальная стилизация, правка и генерация на Qwen-Image-2.1

Локальная стилизация, правка и генерация изображений на **Qwen-Image-2.1**: переносит вашу картинку
в выбранный стиль (img2img с сохранением композиции), правит её по инструкции и генерирует кадры с
нуля; инференс полностью локальный — изображение никуда не уходит, начиная с 8 ГБ VRAM (профили
`VRAM8`/`VRAM12`/`VRAM16`).

Стиль — это выбор: аниме-адаптер FUSAL R80 включают пресеты с суффиксом `-anime` (и флаг
`--lora-scale`), пресеты без суффикса работают без стилевого адаптера (`lora 0`) и просто следуют
промту.

> **18+ / NSFW.** Проект рассчитан на взрослую аудиторию и создан для NSFW-генерации: промты,
> референсы и результаты могут содержать взрослый контент. Используя пакет, вы подтверждаете, что
> вам есть 18 лет и что такой контент законен в вашей юрисдикции. Модели скачиваются с HuggingFace
> под их собственными лицензиями — ответственность за использование лежит на вас.

Требования: Python **3.12**, CUDA-сборка torch (Linux/Windows, ставится установочным скриптом),
VRAM/RAM/диск — по профилю машины (см. таблицы ниже: 8 ГБ VRAM / 16 ГБ RAM — минимум для `VRAM8`).

## Quick start

### 1. Install

Windows:

```bat
bootstrap.cmd -Profile VRAM12
```

Linux / macOS:

```bash
./bootstrap.sh VRAM12
```

Скрипт делает всё по шагам: создаёт `.venv`, ставит пакет с CUDA-индексом torch, печатает план
загрузки моделей профиля (репозиторий → компоненты → ГиБ → лицензия → нужен ли `HF_TOKEN`),
скачивает их, запускает `env` и `selftest`, затем печатает готовую команду `gen`.
Проверить доступ к весам **без скачивания** (по одному маленькому файлу на репозиторий):
`bootstrap.cmd -Profile VRAM12 -Check` (Linux: `./bootstrap.sh VRAM12 --check`).
План без установки и загрузки: `-DryRun` / `--dry-run`.

### 2. Положите промт и референсы

```text
prompts/
  my-scene/
    refs/               # референсы: любые имена, до 10 файлов
      01-face.png
      02-room.jpg
    prompt-qwen.txt     # промт Qwen (tag сессии — qwen)
    prompt-h3.txt       # опционально: промт H3 (tag — h3)
    project.yaml        # опционально: preset + параметры запуска (см. ниже)
```

- Расширения референсов: `.png`, `.jpg`, `.jpeg`, `.webp`; имена файлов любые.
- Порядок — natural sort по имени: `2-x.png` раньше `10-x.png`; он же задаёт `<image1>`, `<image2>`.
- Дубликат имени (`a.png` + `a.jpg`) — берётся первый, в лог пишется предупреждение.
- Больше 10 картинок — берутся первые 10, в лог пишется, кого отбросили (предел модели).
- Картинок может не быть вовсе — для моделей с поддержкой T2I (тогда пропорцию кадра задаёт `--aspect`,
  без него — `1:1`).

`project.yaml` — необязательный конфиг проекта: `preset` именем/путём или inline-пресетом
(`preset: {extends: base, size_px: 960}`), `prompt`, `refs`, `out`, `seeds`/`count` и любые поля
`RunConfig` (`aspect`, `generation: {steps: 8}`, `upscale: {factor: 1.5}`). Флаги CLI главнее yaml.

### 3. Сгенерируйте

```bash
python -m qwenstyle gen --preset VRAM12 --prompt my-scene/prompt-qwen --count 4
```

Вместо `--count 4` можно перечислить сиды: `--seeds 84,32-38`. Если не указать ни то, ни другое —
будет один случайный сид (он печатается и попадает в имя файла). `--project my-scene/project.yaml`
заменяет `--preset` (и любые другие настройки) значениями из конфига проекта.

Результат — папка сессии `prompts/my-scene/out/202611162054-qwen/`:

```text
prompts/my-scene/out/202611162054-qwen/
  84-25.png  85-25.png  86-25.png  87-25.png   # кадры: <seed>-<steps> (после апскейла)
  84-25-gen.png …                             # чистая генерация, если апскейл включён
  84-25.log                                   # весь вывод этого кадра: [plan], [cache], [gen], [done]
  meta.json                                   # один на сессию: параметры, проект/промт, кадры, тайминги
```

Как это выглядит в консоли (числа — с нашей машины, см. таблицу пресетов):

```text
[gen] проект prompts/my-scene (только CLI)
[gen] пресет VRAM12-release · backend qwen_image21 · 25 шагов · lora 0 · энкодер heretic
[gen] промт prompts/my-scene/prompt-qwen.txt (md5 4819c8e1ddc4)
[gen] референсы 1: 01-face.png → <image1>
[gen] сиды 4: <четыре случайных сида печатаются здесь>
[gen] сессия prompts/my-scene/out/202611162054-qwen
[plan] input prompts/my-scene/refs/01-face.png (768x768, 1 референс) -> crop 960x960
[gen] seed <N>: <время>s 960x960 peak 6.2 GiB
[gen] итог: 4 кадр(ов) в prompts/my-scene/out/202611162054-qwen · всего <сумма>s · среднее <…>s/кадр
```

## Модели здесь не хостятся

В репозитории **только код**, манифесты и скрипты загрузки — весов, кэшей и примеров NSFW-кадров
в нём нет. `bootstrap.*` / `python -m qwenstyle models download --profile …` скачивают веса прямо
с HuggingFace под их лицензиями; ничего не публикуется и не перезаливается.

| репозиторий | что это | лицензия | gated |
|---|---|---|---|
| `Qwen/Qwen-Image-2.1` | базовая модель: transformer + text-encoder + VAE (≈30.9 ГиБ bf16) | Apache-2.0 | нет |
| `Qwen/Qwen-Image-2.1-Turbo` | distill-трансформер (8 шагов); энкодер и VAE берутся из base | Apache-2.0 | нет |
| `MicksHF/Qwen-Image-2.1-Anime-Fusal` | адаптеры FUSAL: R80 (base) и Turbo E6 R128 | лицензия в карточке репозитория | нет |
| `DreamFast/Qwen3-VL-8B-Heretic-1.3.0` | текст-энкодер heretic 8B (16.33 ГиБ bf16) — **умолчание** | Apache-2.0 | **да** |
| `MiniMaxAI/MiniMax-H3-Image` | 33.13B, 6 шагов PDD, T2I и edit (профиль `VRAM16`) | MiniMax H3 Community License | нет |
| `llmfan46/Qwen3-VL-32B-Instruct-ultra-uncensored-heretic` | 32B-энкодер для H3-Image (62.14 ГиБ bf16) | Apache-2.0 | нет |

Gated-репозиторий (`DreamFast/Qwen3-VL-8B-Heretic-1.3.0`) требует принять лицензию на сайте
HuggingFace и передать токен: `export HF_TOKEN=…` (PowerShell: `$env:HF_TOKEN = "…"`). Без него
`models download`/`--probe` возвращают код 2 с подсказкой.

Не в публичных профилях (только для разработки, см. [`docs/DEVELOPMENT.md`](docs/DEVELOPMENT.md)):
бекенд FLUX.2 klein — у него **FLUX Non-Commercial License v2.1** (только некоммерческое
использование; пресетов в наборе нет) — и SeedVR2-3B, апскейлер, который пока не доведён
до стабильного состояния.

## Ваша машина → профиль → одна команда

| машина | профиль | диск | целевой кадр | загрузка моделей | первый прогон |
|---|---|---|---|---|---|
| 8 ГБ VRAM / 16 ГБ RAM | **VRAM8** | ≈ 75 ГиБ | 1080p | `python -m qwenstyle models download --profile VRAM8 --yes` | `python -m qwenstyle gen --preset VRAM8 --prompt my-scene --count 4` |
| 12 ГБ VRAM / 32 ГБ RAM | **VRAM12** | ≈ 55 ГиБ | 960p native (1440 — `--upscale 1.5`) | `python -m qwenstyle models download --profile VRAM12 --yes` | `python -m qwenstyle gen --preset VRAM12 --prompt my-scene --count 4` |
| 16 ГБ VRAM / 64 ГБ RAM | **VRAM16** | ≈ 181 ГиБ | 1440p native; 2160 — `4k-fast`/`r3-*` | `python -m qwenstyle models download --profile VRAM16 --yes` | `python -m qwenstyle gen --preset VRAM16 --prompt my-scene --count 4` |

Профиль — это данные ([`qwenstyle/profiles.py`](qwenstyle/profiles.py)): список репозиториев,
адресованные пресеты, след на диске и целевая высота кадра. План без скачивания:
`python -m qwenstyle models download --profile VRAM12 --dry-run`; проверка доступа без полной
загрузки: `--probe`.

Чем профили отличаются по существу:

- `VRAM8` — энкодер работает **на CPU** с диск-стримингом весов (90–126 с на новую пару «промт +
  картинка + сетка»). Черновик `*-preview` — 480p и 8 шагов без апскейла, финал `*-release` — 640p
  (в `-anime` — базовая модель с FUSAL 0.7 и 25 шагов) + ESRGAN до 1080p; без суффикса `-anime`
  оба этапа идут на Turbo (8 шагов). Первая правка промта дорогая, дальше всё берётся из кэша
  эмбеддингов.
- `VRAM12` — энкодер на GPU (`device: auto` → `cuda` + конвейер стриминга, 15–16 с), 768p черновик
  с `offload: group` / 960p финал **native без апскейла** (`upscale: null`); KV префикса в RAM
  (`kv_cache: offload`) — так профиль честно влезает в 12 ГиБ. LoRA FUSAL по умолчанию выключена
  (`lora 0`), anime-пресеты включают её на 0.7.
- `VRAM16` — то же железо, но 64 ГБ RAM: добавляются MiniMax-H3-Image (33.13B, T2I + edit) и
  32B heretic-энкодер, финал — 1440p native (`upscale: null`), 4K — `VRAM16-4k-fast` (1088p →
  ESRGAN 2160) или `VRAM16-r3-*` (3 референса → 2160). На 32 ГБ RAM этого
  профиля нет: H3 держит 30.9 ГиБ fp8-трансформера в RAM при групповом offload.

Как читаются веса энкодера при стриминге: по заголовку safetensors вычисляется точное смещение
тензора, и ровно его байты читаются позиционно (`seek + readinto` под замком) — **без mmap** и без
`safetensors.safe_open`. На CPU-пути данные идут в обычный буфер, на GPU-пути — прямо в pinned-буфер
конвейера, то есть на одну копию меньше. Поэтому открытие шарда не списывается в commit целиком:
62.13 ГиБ весов 32B-энкодера в трёх шардах дают **+0.00 ГиБ** commit вместо **+62.37 ГиБ** у
`safe_open`, а всё чтение этих весов добавляет +14.45…15.3 ГиБ commit — это дельта процесса
фазы энкодинга от baseline, снятого до его старта (вместе с самим процессом), а не объём данных;
пиковая занятость pinned-пула на всех 62.13 ГиБ — 4.37 ГиБ (`peak_uss`). Скорость: на холодных
данных новый путь не медленнее прежнего (2.58 против 2.53 ГиБ/с — оба упираются в диск), на тёплом
page cache — медленнее (6.5–8.1 против 19.5–21.2 ГиБ/с). Тёплый проход возвращается к ~19 ГиБ/с
через `mmap.mmap` самого файла (не `safetensors`) — это отдельная работа; математика от способа
чтения не зависит: эмбеддинги те же бит-в-бит.

Расчёт настроек под своё железо: [`renderkit/`](renderkit/) (JS, без зависимостей) — калькулятор
«целевая картинка + VRAM/RAM/диск → самодостаточный YAML» с оценками VRAM, RAM и времени кадра.
Он не знает имён пресетов и выдаёт файл под любым именем (`run --config`, `gen --preset`);
подробности и контракт — [`renderkit/README.md`](renderkit/README.md).

## Справочник `gen`

```text
python -m qwenstyle gen [--preset PRESET] [--prompt NAME | --project PATH]
                        [--out DIR] [--seeds SPEC | --count N]
                        [--aspect R] [--upscale F|null] [--set KEY=VALUE] [--dry-run] [--no-logs]
```

| флаг | что делает |
|---|---|
| `--preset` | тариф/пресет. Шорткаты: `VRAM8`/`VRAM12`/`VRAM16` = `<тариф>-release`; `VRAM12-preview`, `VRAM12-release`, `VRAM12-preview-anime`, `VRAM12-release-anime`, `VRAM12-anime` = `VRAM12-release-anime`; `VRAM16-4k-fast`; либо точное имя любого пресета из `qwenstyle/presets/` |
| `--prompt NAME` | проект промта: `<project>/<prompt-stem>` (например `my-scene/prompt-qwen`, `.txt` можно опустить) или `<project>`, если в нём ровно один `*.txt`. Референсы — `<project>/refs/`, результаты — `<project>/out/` |
| `--project PATH` | `project.yaml` (файл, каталог или имя проекта в `prompts/`): preset + любые поля `RunConfig`; флаги CLI главнее yaml. `--project` + `--prompt` меняет только промт |
| `--out DIR` | каталог **сессий** (по умолчанию `<project>/out`); сессия — `<YYYYMMDDHHMM>-<tag>` внутри него |
| `--count N` | N случайных сидов (печатаются), взаимоисключающе с `--seeds` |
| `--seeds SPEC` | явные сиды: `84`, `32-38`, `1,7,42`; без обоих флагов — один случайный сид |
| `--aspect R` | пропорция кадра (`16:9`, `4:3`, `1:1`) вместо пропорции первого референса; для T2I без флага — `1:1` |
| `--upscale F\|null` | число — множитель апскейла (`target_height` пресета главнее); `null`/`none`/`off` — выключить апскейл целиком (native-кадр, без `<seed>-<steps>-gen.png`) |
| `--set KEY=VALUE` | параметр кубика путём его параметра (`transformer.qwen_image21.steps=8`, `encoder.qwen3vl.device=cpu`, `source.frame.height=1088`); можно повторять, полный список — `python -m qwenstyle cubes show <id>` |
| `--dry-run` | только план: сетка, ключ кэша эмбеддингов, будет ли энкод, апскейл, папка сессии; веса не грузятся |
| `--no-logs` | не писать `<кадр>.log` (кадры и `meta.json` сессии остаются) |

Что происходит с картинками: референсы из `refs/` сортируются естественно (`2-x` < `10-x`), лишние
сверх `max_images` бекенда (у Qwen-Image-2.1 и H3 — 10) отбрасываются с записью в лог. Кроп кадра
считается по **первому** референсу; пропорция — по нему же, если не задан `--aspect`.

Имена файлов: `<seed>-<steps>.png` — итоговый кадр (после апскейла), `<seed>-<steps>-gen.png` —
чистая генерация, она появляется только когда апскейл действительно включён; рядом лежит
`<seed>-<steps>.log`, а **один** `meta.json` на всю сессию (кадры, их тайминги, итоги). Сессия —
`prompts/<project>/out/<YYYYMMDDHHMM>-<tag>/` (`-2` при коллизии минуты).

Смотреть на кадры «пачкой» дешевле, чем по одному: внутри одной сетки `--seeds`/`--count`, `--steps`
и `--lora-scale` бесплатны (кэш эмбеддингов тот же), платится только генерация.

## Пресеты и измеренное время кадра

17 публичных пресетов: `VRAM8-*` (4), `VRAM12-*` (4), `VRAM16-*` (9). Имя с `-anime` включает
адаптер FUSAL; без него стиль не навязывается. Полная таблица (включая размеры PNG и разбор
«первый прогон против повторного») — [`docs/bench/presets.md`](docs/bench/presets.md); там же
условия замера; влезаемость тарифов проверена отдельно — [`docs/bench/vram-tiers.md`](docs/bench/vram-tiers.md).

Условия: **RTX 4080 16 ГБ VRAM / 63.6 ГБ RAM**, Windows 11, torch 2.8.0+cu129, `HF_HUB_OFFLINE=1`,
прогретый page cache весов, `seed=1`, один квадратный референс 768×768. Поэтому все сетки ниже
квадратные: 480×480, 640×640, 960×960… На референсе 16:9 того же размера сетка больше по площади
в 1.78×, и время генерации растёт примерно пропорционально числу токенов (например
`VRAM16-release` 1440p 16:9 — 205 с вместо 96 с).

|---|---|---|---|---|---|
| `VRAM8-preview` | 8 ГБ / 16 ГБ | 480p | 480×480 | 113 (энкод CPU cold) | 4.1 |
| `VRAM8-release` | 8 ГБ / 16 ГБ | 640p | 1080×1080 | 150 (энкод CPU cold) | 5.0 |
| `VRAM8-preview-anime` | 8 ГБ / 16 ГБ | 480p | 480×480 | 22 | 4.1 |
| `VRAM8-release-anime` | 8 ГБ / 16 ГБ | 640p | 1080×1080 | 26 | 4.9 |
| `VRAM12-preview` | 12 ГБ / 32 ГБ | 768p | 768×768 | 39 (энкод GPU cold) | 3.9 |
| `VRAM12-release` | 12 ГБ / 32 ГБ | 960p | 960×960 native | 71 (энкод GPU cold) | 4.5 |
| `VRAM12-preview-anime` | 12 ГБ / 32 ГБ | 768p | 768×768 | 24 | 3.9 |
| `VRAM12-release-anime` | 12 ГБ / 32 ГБ | 960p | 960×960 native | 49 | 4.5 |
| `VRAM16-preview` | 16 ГБ / 64 ГБ | 768p | 768×768 | 21 | 10.3 |
| `VRAM16-preview-anime` | 16 ГБ / 64 ГБ | 768p | 768×768 | 21 | 10.3 |
| `VRAM16-release` | 16 ГБ / 64 ГБ | 1440p | 1440×1440 native | 125 (энкод GPU cold) | 6.2 |
| `VRAM16-release-anime` | 16 ГБ / 64 ГБ | 1440p | 1440×1440 native | ≈125 | ≈6.2 |

| `4K-slide` | 16 ГБ / 64 ГБ | 4K + slide | 3840×2176 native | 513 (3 референса 16:9) | 13.8 |
| `VRAM16-4k-fast` | 16 ГБ / 64 ГБ | 1088p | 2160×2160 | 80 | 4.7 |
| `VRAM16-r3-169` | 16 ГБ / 64 ГБ | 912p + 16:9 | 3934×2160 | — (3 референса, не мерялось) | — |
| `VRAM16-r3-43` | 16 ГБ / 64 ГБ | 1056p + 4:3 | 2880×2160 | — (3 референса, не мерялось) | — |

Что читается из таблицы:

- **Время кадра** — весь процесс от старта до сохранённого PNG (`[done] … total`), включая загрузку
  модели и энкод. Апскейл дешёвый: 0.4–1.3 с на кадр вплоть до 2160×2160.
- **`-anime` = LoRA FUSAL 0.7** и по времени бесплатен: разница с пресетами без `-anime` — в пределах шума
  (LoRA меняет веса трансформера, а не число шагов). Черновики — 8 шагов, релизы — 25.
- **Черновики дешёвые, финалы — нет**: `VRAM16-preview` (768p, 8 шагов) — 21 с против 125 с у
  `VRAM16-release` (1440p, 25 шагов); `VRAM16-4k-fast` даёт 2160×2160 за 80 с ценой
  синтетической текстуры от ESRGAN ×1.985.
- **`offload: group` виден по пику VRAM, а не по времени**: `VRAM12-preview` (768p с offload) —
  3.9 ГиБ / 10.3 с, `VRAM16-preview` (тот же кадр без offload) — 10.3 ГиБ / 8.2 с.
- **Первый прогон против повторного** (та же пара «промт + картинка», новый процесс): `VRAM8-preview`
  113 → 22 с (−91 с, энкод был 90 с), `VRAM12-preview` 39 → 24 с, `VRAM12-release` 71 → 49 с.
  Критичен кэш эмбеддингов только для `VRAM8-*` (CPU-энкод 90–126 с); у `VRAM12-*`/`VRAM16-*`
  GPU-энкод — 15–16 с, то есть 15–20 % прогона.

**Выключатель апскейла.** `upscale: null` в пресете или `--upscale=null` в `run`/`gen` выключает
апскейл **целиком**: кадр отдаётся native, пары `<seed>-<steps>-gen.png` не появляется (именно так работают
`VRAM12-release*` и `VRAM16-release*`). `factor: 0` сам по себе апскейл **не выключает** —
`target_height` пресета главнее, поэтому `--upscale 0` при `upscale.target_height: 1440` всё равно
гонит ESRGAN (1440 / 1088 → ×1.32); выключить — `--upscale=null` или
`--set post.upscale.esrgan.target_height=0`. Пары `<seed>-<steps>-gen.png` появляются только при включённом апскейле:
u `VRAM8-release*`, `VRAM16-4k-fast`, `VRAM16-r3-*` и при явном `--upscale F`.

## KV-кеш референсов (`kv_cache`)

На шаге 0 трансформер считает префикс — текст промта плюс **все** референсы — и кладёт его K/V
в кеш, чтобы 8 или 25 шагов досчитывать только сам кадр. Кеш стоит **512 КиБ на префиксный токен**
(`32 слоя × 32 головы × 128 × K+V × 2 Б`) и по умолчанию живёт в VRAM. Режимы — `generation.kv_cache`
(умолчание в `presets/base.yaml` — `auto-offload-ref2`):

| значение | где K/V | когда включается сам | цена |
|---|---|---|---|
| `auto-offload-ref2` | — | **умолчание**: `true` на 1 референсе, `offload` на 2+ | — |
| `true` | VRAM | 1 референс | быстро, но объём префикса влезает не всегда |
| `offload` | RAM, подкачка послойно (212 МиБ на слой) | 2+ референса | **+13 % времени**, −3.7…−6.5 ГиБ VRAM |
| `false` | без кеша, префикс считается каждый шаг | вручную | ~2× медленнее, но VRAM минимум |

Замеры (RTX 4080 16 ГиБ, 1376×768 и 1920×1088; полный разбор —
[`docs/bench/kv-cache-offload.md`](docs/bench/kv-cache-offload.md)):

| кейс | `kv_cache` | генерация | пик VRAM |
|---|---|---|---|
| 768p, 8 шагов, 1 референс | `true` | 14 с | 15.2 ГиБ |
| 768p, 8 шагов, 1 референс | `offload` | 16 с | 11.5 ГиБ |
| 768p, 8 шагов, 2 референса | `true` | **OOM** на шаге 0 | — |
| 768p, 8 шагов, 2 референса | `offload` | 21 с | 12.0 ГиБ |
| 1088p, 25 шагов, 1 референс | `true` | 93 с | 13.7 ГиБ |
| 1088p, 25 шагов, 1 референс | `offload` | 105 с | **7.2 ГиБ** |
| 768p, 8 шагов, 3 референса | `true` | **OOM** на шаге 0 | — |
| 768p, 8 шагов, 3 референса | `offload` | 24 с | 13.1 ГиБ |

Что из этого следует:

- **Порог — не разрешение, а объём префикса** (`≈1230 токенов текста + референсы × токены кадра`):
  на 768p один референс (префикс 5358) влезает, два (9492) — уже нет.
- `offload` не меняет картинку: пара `true`/`offload` на одном seed даёт **побайтно тот же** PNG.
- Переопределить: `--set strategy.kv_offload.mode=offload` (или `true`/`false`), в пресете —
  `strategy.kv_offload.mode: …`.

## Скользящее окно внимания (`window_attn_px`)

Режим больших канвасов, устроенный как context windows в ComfyUI: **кадр считается один раз на
весь канвас** (один латент, глобальные позиции), режется только сам attention — каждая полоса
запросов видит префикс (текст + референсы) и свою окрестность по строкам. Выходы не усредняются,
швов не бывает по построению. Это не тайловый денойзинг: модель не запускается по кускам.

```text
--set strategy.window_attention.window_attn_px=384        # высота полосы, px (0 = выкл)
--set strategy.window_attention.window_attn_margin_px=384 # запас строк сверху/снизу
--set source.frame.ref_crop_side=960                # сетка референсов вместо канваса
```

**Гейт корректности:** если `window_attn_px` ≥ высоты канваса, остаётся одна полоса = штатное
плотное внимание, и кадр обязан совпасть с нативным **побитово**. Проверено: 480p/8 шагов —
`max diff 0`. Любую правку процессора проверять этой парой первой.

Замеры (nita-atomic, 2 референса, 25 шагов, seed 20261113, RTX 4080 16 ГиБ, `offload=group`;
кадры — `out/bench/sliding/`):

| канвас | режим | время | пик VRAM | качество |
|---|---|---|---|---|
| 1696×960 | нативный | 104 с | 7.1 ГиБ | — |
| 1696×960 | полоса 384 + запас 128 (4250 из 6360 токенов) | **96 с** | 7.1 ГиБ | корректно, швов и ряби нет |
| 1920×1088 | нативный / полоса 384 + 128 | 125.9 / **123.3 с** | 7.4 ГиБ | оба корректны |
| 3200×1792 | нативный | 376 с | 10.3 ГиБ | дублированный хвост, красная полоса через кадр |
| 3200×1792 | полоса 384 + 128 (**36 %** канваса видит полоса) | 281 с | 10.3 ГиБ | **сломано: сцена размножилась по вертикали** |
| 3200×1792 | полоса 384 + 384 (**64 %**) | **314 с** | 10.3 ГиБ | корректно; резкость 14.8 против 15.2, рябь ниже (4.0 против 4.7) |

### Ограничения

- **Покрытие контекста ≥ ~⅔ канваса.** У изображения нет непрерывности вдоль порядка токенов,
  поэтому полоса-«панорама» для модели сама по себе является целой картинкой: при покрытии 36 %
  каждая полоса нарисовала свою сцену и они сложились в две вертикальные копии; при 64 % всё
  корректно. Это главный ограничитель режима, и обойти его «правильной настройкой» нельзя.
- **VRAM он не экономит** в рабочей зоне: 1792p — 10.3 ГиБ и с ним, и без него. Экономия памяти
  была бы ровно там, где покрытие падает ниже порога, то есть там, где картинка ломается.
- **Потолок разрешения не поднимает.** Выше ~8192 латентных токенов (2048×2048 = 4.2 Мп)
  планировщик модели работает вне своей полосы, и никакая схема внимания этого не меняет.
- **Референсы обязаны быть мельче канваса** (`ref_px`) начиная примерно с 1600p: энкодер видит
  каждое изображение референса, и на сетке канваса прогон падает в OOM на фазе `[4/5]`, задолго
  до генерации. Сетка референсов должна быть кратна **32** (`image_processor` усекает кадр до 32).
- **Опирается на внутренности diffusers 0.43.0.dev0** (`_qwenimage21_prepare_qkv`,
  `segments`/`key_valid` в `QwenImage21AttnProcessor`). После обновления diffusers первым делом
  прогнать гейт «одна полоса == нативно».
- Полосы режутся **по строкам** (полная ширина), а не квадратами: так срез токенов остаётся
  непрерывным и слоты `img_shapes` не разъезжаются.

### Готовые пресеты с этим режимом

| пресет | кадр | полоса / запас | покрытие | замер |
|---|---|---|---|---|
| `VRAM16-large` | 3200×1792 (1792p) | 384 / 384 px | 64 % | 314 с, 10.3 ГиБ, 2 референса |
| `4K-slide` | 3840×2176 (4K UHD) | 1088 / 448 px | 91 % | 513 с, 13.8 ГиБ, 3 референса |

Оба рендерят native без апскейла (`upscale: null`) и держат LoRA 0.0. Референсы у них считаются на
уменьшенной сетке (`ref_px`): 960 у `VRAM16-large` (2 референса) и 768 у `4K-slide` — на 4K сетка
960 физически не проходит: 3 × 1664×960 = 18 720 токенов префикса, энкодер падает в OOM на `[4/5]`.
Правило простое: **сумма токенов референсов ≤ ~12–13 тыс.**, то есть `ref_px ≈ 768` на трёх
референсах и 960–1024 на одном–двух.

Замер `4K-slide` (nita-camp-re, 3 референса, seed 20261113, 25 шагов): генерация 513 с, всего 542 с,
пик 13.8 ГиБ, кадр 3840×2176. Размножения сцены нет, швов нет; на границе полос (y≈1088) остаётся
мягкая ступенька 2.26 по градиенту, рябь 5.9× медианы спектра на периоде 32 px — это уже стоимость
8.3 Мп, а не режима.

### Когда имеет смысл

- **Стоит включать на 1600p–2304p**: там он даёт ~1.2× по времени (376 → 314 с на 1792p), чуть
  меньше высокочастотной ряби и не приносит артефактов тайлинга. Полосу брать 384–512 px, запас —
  не меньше полосы, чтобы покрытие осталось ≥ ⅔.
- **Не нужен на 480p–1080p**: нативный режим влезает и идёт не медленнее.
- **Не использовать как способ «дожать» разрешение** сверх ~2048p: качество определит полоса
  модели, а не внимание — для больших кадров честнее нативный рендер 1080–1792p + апскейл
  (ESRGAN или H3, см. соседние разделы).
- **Не включать «на всякий случай» в публичных пресетах**: по умолчанию `window_attn_px=0`, режим —
  осознанный флаг под конкретный кадр.

```bash
# 1792p, полоса 384 с запасом 384 (покрытие 64 %), референсы на сетке 960p
python -m qwenstyle gen --preset VRAM16-release --prompt my-scene --aspect 16:9 --seeds 84 \
  --set size_px=1792 --set source.frame.ref_crop_side=960 \
  --set strategy.window_attention.window_attn_px=384 \
  --set strategy.window_attention.window_attn_margin_px=384
```

## Сборка пайплайна из кубиков

Пайплайн описан стадиями-кубиками (14 штук в реестре), и их можно смотреть и проверять **без
загрузки весов и без GPU**:

```text
python -m qwenstyle cubes list                     # id, стадия, порты, параметры, бюджет
python -m qwenstyle cubes show decoder.vae.qwen21  # параметры с диапазонами и описанием
python -m qwenstyle cubes test                     # self_test всех кубиков (секунды)
python -m qwenstyle cubes schema | --json          # JSON Schema (draft-07) для конструктора
python -m qwenstyle compose --spec pipeline.yaml --check   # проверить композицию из файла
```

Цепочка кадра читается так: `source.frame` (канвас и сетка референсов → порт `frame`) +
`source.txtFileImage` (промт из `.txt` и явные референсы `Image1…Image10` → `prompt`+`refs`) →
`encoder.qwen3vl` (`prompt`+`frame` → `conditioning`, референсы читает) →
`transformer.qwen_image21` (`conditioning`+`frame` → `latents`,
требует стратегии `strategy.precision.fp8` и `strategy.kv_offload`) → `decoder.vae.qwen21`
(`latents` → `frames`, тензор) → `decoder.postprocess.image` (`frames` → `pixels`) →
`post.upscale.esrgan` / `post.colorfix` (`pixels` → `pixels`). Промежуточный порт `frames`
отделяет декодирование от формата результата: рядом с картинкой в будущем встанет
`decoder.postprocess.video` без правки декодера.

Файл композиции — обычный YAML, его понимает `compose --check`:

```yaml
name: my-frame
inputs: [prompt, refs]
cubes:
  - id: source.frame
    params: {height: 768, width: 0, ref_crop_side: 0}
  - id: source.txtFileImage
    params: {prompt: prompt-qwen.txt, Image1: refs/01-input.png}
  - id: encoder.qwen3vl
  - id: strategy.precision.fp8
  - id: strategy.kv_offload
    params: {mode: offload}
  - id: transformer.qwen_image21
    params: {steps: 25, offload: group}
  - id: decoder.vae.qwen21
  - id: decoder.postprocess.image
```

Несовместимая цепочка отклоняется до запуска: `compose --check` печатает коды
(`port_missing`, `ports_unused`, `strategy_missing`, `param_unknown`, `stage_order`) и возвращает
код 1. Дерево конкретного пресета показывает `python -m qwenstyle config show <preset> --cubes`
(то же — `run --cubes`, `gen --cubes`).

## Кеши и диск

| что | где | можно ли чистить |
|---|---|---|
| кэш эмбеддингов промта и картинок | `cache/embeds/` (`embeds_<md5>_<sha>_<тег>_<W>x<H>.pt` + `.json`; `text_embeds_…` — у моделей с внутренним conditioning) | **да**: `python -m qwenstyle cache prune …` (без `--apply` — только план), плюс автоматическое вытеснение политикой `cache_supersede` (умолчание `pair`: сменил промт или картинку → старые записи этой пары удаляются отложенно в конце прогона) |
| кэш моделей: fp8-квантование и локальные веса | `cache/models/` — `fp8_transformer*` (base / turbo / flux2 / h3_image) и `weights/` (энкодеры heretic 8B/32B, ESRGAN) | **нет**: не вытесняется никогда; пересборка квантования — только `--rebuild-fp8-cache` |
| исходные веса моделей | `hf-cache/` (`HF_HOME`), каноническая раскладка `blobs/` + симлинки `snapshots/<commit>/` | вручную, если не нужны |

`python -m qwenstyle env` печатает фактический размер каждого кэша, свободную VRAM/RAM и диск:

```text
[cache]
  cache/embeds: 19 записей, 243.2 MiB, сеток: 13 (…) — вытесняется (`cache prune`, `cache_supersede`)
  cache/models: 5 объект(ов), 131.2 GiB — не вытесняется никогда (пересборка: --rebuild-fp8-cache)
    cache/models/fp8_transformer: 6.6 GiB
    cache/models/weights: 78.5 GiB
[disk]
  G:\Work\nsfw-style свободно 116.9 GiB из 931.5 GiB
```

Сколько занимает профиль целиком (загрузка + производные кэши): `VRAM8` ≈ 75 ГиБ, `VRAM12` ≈ 55 ГиБ,
`VRAM16` ≈ 181 ГиБ — эти числа печатает и `models download --profile … --dry-run`.

Как удалить скачанное: отдельной команды «стереть всё» нет, потому что кеши разделены по смыслу.
Удалить кэш эмбеддингов — `python -m qwenstyle cache prune --all --apply` (или просто удалить
`cache/embeds/`). Удалить веса и квантование — вручную `hf-cache/` и `cache/models/`; после этого
`models download --profile …` и первый прогон создадут их заново (см. ниже про цену).

## Почему первый прогон дольше

Две вещи считаются один раз и потом лежат на диске:

1. **fp8-квантование трансформера** (`cache/models/fp8_transformer*`): bf16 → fp8 каст в base-профиле —
   ≈26 с каста + ≈14 с записи 6.7 ГиБ, у H3-Image — 202.8 с на 30.9 ГиБ. Второй старт читает готовый
   кэш (0.4–0.6 с).
2. **Эмбеддинги промта и картинок** (`cache/embeds`): `VRAM8-*` — CPU-энкод 90–126 с на новую пару
   «промт + картинка + сетка», `VRAM12-*`/`VRAM16-*` — GPU-энкод 15–16 с (стриминг весов энкодера);
   из кэша — 0 с.

Отсюда рабочий порядок: зафиксировать картинку и промт → подобрать всё на дешёвом черновике
(`*-preview`, 8 шагов) → один финальный прогон. Любая правка текста промта, другой файл референса
или другая сетка (`--aspect` в `gen`, `--size`/`--resolution` в `run`) = новый энкод. А `--seeds`,
`--count`, `--steps`, `--lora-scale` бесплатны — они не меняют conditioning.

Ограничения по железу (проверено):

- **8 ГБ VRAM** — только профиль `VRAM8` (групповой offload, энкодер на CPU). 768p без offload,
  H3-Image сюда тоже не влезает.
- **12 ГБ VRAM** — `VRAM12`: 768p черновик и 960p финал идут с `offload: group` и `kv_cache: offload`
  (без них пик 11–16 ГиБ — это уже не 12 ГБ).
- **16 ГБ VRAM** — `VRAM16`; 1440p требует `offload: group` (в пресетах он уже выставлен).
- **32 ГБ RAM** — без H3-Image: групповой offload держит 30.9 ГиБ fp8-трансформера в RAM, поэтому
  `VRAM16` (`h3-image`) нужны 64 ГБ.
- Нативный 1440p больше не добирается апскейлом: `VRAM16-release` отдаёт 2560×1440 как есть
  (25 шагов — 205 с на 16:9, 96 с на квадрате); `VRAM16-4k-fast` даёт 2160 из 1088p вдвое-втрое
  дешевле, а `VRAM12-release` — 960p native (1440 — явным `--upscale 1.5`).

## Проверка установки

```bash
python -m qwenstyle selftest --profile VRAM12
```

`selftest` проверяет окружение (версии, CUDA, свободные VRAM/RAM/диск), наличие весов и
fp8-кэша профиля и делает один дешёвый рендер 480p/4 шага на синтетической картинке из памяти
(проверяется размер и то, что кадр не пустой). Коды возврата: 0 — всё в порядке, 2 — чего-то не
хватает (веса профиля), 1 — ошибка. Полезные варианты: `--dry-run` (только проверки, без рендера)
и `--json`. Этот же selftest запускает установочный скрипт в конце.

## Про `bootstrap.ps1` напрямую

Запускать `bootstrap.ps1` руками в PowerShell обычно не нужно: после скачивания ZIP с GitHub у
файлов появляется зона MOTW, и PowerShell отказывается исполнять скрипт
(`… cannot be loaded because running scripts is disabled on this system`). `bootstrap.cmd` — тонкая
обёртка, которая снимает метку (`Unblock-File` для `*.ps1` в папке) и вызывает PowerShell с
`-NoProfile -ExecutionPolicy Bypass`, не меняя политику в системе. Если запускаете `.ps1` напрямую,
сделайте то же самое:

```powershell
Get-ChildItem *.ps1 | Unblock-File
powershell -NoProfile -ExecutionPolicy Bypass -File .\bootstrap.ps1 -Profile VRAM12
```
